# SGLang 和 RadixAttention — 面向前缀密集型工作负载

> SGLang 将 KV 缓存视为一等、可重用的资源，存储在基数树（Radix Tree）中。vLLM 以先来先服务（FCFS）方式调度请求，而 SGLang 的缓存感知调度器优先处理共享前缀更长的请求 — 本质上是深度优先的基数树遍历，使热分支驻留在 HBM 中。在使用 ShareGPT 风格 1K 提示的 Llama 3.1 8B 上，SGLang 达到约 16,200 tok/s，而 vLLM 约 12,500，优势约 29%。在前缀密集的 RAG 工作负载上，优势可达 6.4 倍。在语音克隆风格的工作负载上，缓存命中率超过 86%。2026 年部署在 40 万+ GPU 上，覆盖 xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS。关键点在于，当前缀排序不一致时，6.4 倍的优势会消失 — 排序是工程师的杠杆。

## 学习目标

- 画出 RadixAttention：前缀如何存储在基数树中，KV 块如何在同一分支根下的序列间共享。
- 解释缓存感知调度，以及为什么 FCFS 对前缀密集型流量是错误的。
- 给定前缀缓存命中率和提示长度分布，计算工作负载的预期加速比。
- 命名使 6.4 倍数字成真的提示排序规范，而非失去的优势。

## 问题所在

经典服务将每个请求的提示视为不透明的。即使 5000 个 RAG 请求都以相同的 2000 token 系统提示加相同检索前言开始，vLLM 也会对那个 2000 token 前缀预填充 5000 次。GPU 一遍又一遍地执行相同的工作。

观察结果：智能体和 RAG 工作负载中的提示几乎总是共享长前缀。系统提示、工具 schema、少样本示例、检索头、对话历史 — 全部在请求间重复。如果你存储一次该前缀的 KV 缓存并重用它，你就不用再次预填充它。

RadixAttention 正是这样做的。token 被索引在基数树中；每个节点拥有从根到该节点路径上的 token 序列的 KV 块。新请求遍历树：任何 token 匹配的节点重用该节点的 KV 块。预填充成本与"新"后缀成正比，而非整个提示。

挑战在于调度。如果两个请求共享 2000 token 前缀，第三个只共享相同前缀的 200 个 token，你想一起服务那两个长共享请求，使长前缀留在 HBM 中。FCFS 恰恰相反 — 它服务先到达的，可能在下一个长前缀请求到来前驱逐热分支。

## 概念说明

### 基数树作为 KV 索引

基数树（压缩前缀树）存储 token 序列。每个节点拥有一个 token 范围及其计算出的 KV 块。子节点扩展一个或多个 token 的序列。

```
root
 |- "You are a helpful assistant..."  (2,000 tokens, 124 KV blocks)
      |- "Context: <doc A>..."        (500 tokens, 31 blocks)
           |- "Question: Alice..."    (80 tokens, 5 blocks)
           |- "Question: Bob..."      (95 tokens, 6 blocks)
      |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

一个新请求带着系统提示 + "Context: <doc A>" + "Question: Carol" 到达。调度器遍历：系统前缀匹配（124 个块重用），doc-A 分支匹配（31 个块重用），然后仅为 "Question: Carol" 分配新块（4 个块）。预填充成本：4 个新 token 块。没有树的情况下：160 个块。预填充节省约 40 倍。

### 缓存感知调度

基于基数树的重用在缓存频繁刷新时毫无意义。两个关键策略：

1. **深度优先调度**。从队列中选择下一个请求时，优先选择与当前运行集根植于同一分支的请求。这使热分支保持固定。
2. **分支级 LRU，而非块级 LRU**。驱逐整个分支（从最少使用的叶节点开始），而非单个块，使缓存形状匹配基数树形状。

FCFS 违反两者。一个共享 2000 token 的请求排在一个共享 50 token 的请求后面，然后 2000 token 分支被驱逐以接纳 50 token 请求。

### 你应该记住的基准数字

- Llama 3.1 8B，H100，ShareGPT 1K 提示：SGLang 约 16,200 tok/s vs vLLM 约 12,500（优势约 29%）。
- 前缀密集型 RAG（相同系统 + 相同文档，不同问题）：SGLang 上最高 6.4 倍。
- 语音克隆工作负载：86.4% 前缀缓存命中率。
- SGLang 客户的生产命中率：50-99%，取决于提示规范。
- 2026 年部署在 40 万+ GPU 上。

### 排序陷阱

6.4 倍的数字依赖于一致的提示模板排序。如果你的客户端在某些请求中构造提示为 `[system, tools, context, history, question]`，在其他请求中为 `[system, context, tools, history, question]`，树就找不到共享前缀。对人类来说看起来像共享前缀的东西，对基数树来说是两个不同的序列。

工程师的杠杆：你的提示模板就是缓存键。固定顺序。将所有不可变内容（系统、工具、schema）放在前面。接着放检索上下文。最后放用户问题。不要将动态内容穿插到前缀中。

研究中的真实案例：将动态内容移出可缓存前缀，一次部署就将缓存命中率从 7% 提升到 74%。

### RadixAttention 的优势和劣势

优势：
- RAG（相同检索前言，不同问题）。
- 智能体（相同工具 schema，不同查询）。
- 带长系统提示的聊天。
- 带重复前言的语音/视觉工作负载。

劣势（回到 vLLM 级吞吐量）：
- 使用唯一提示的一次性生成（代码补全、无系统提示的开放式聊天）。
- 每个请求都将唯一内容穿插到前缀中的动态提示。

### 为什么这是调度器问题，而非仅仅是内核问题

你可以将 KV 重用实现为内核技巧。SGLang 的洞察在于，只有调度器保持热分支驻留时，重用才有回报。朴素的"可用就重用"策略在混合负载下会使缓存频繁刷新。基于基数树索引的调度器才是将内核技巧转化为 29% 生产优势的关键。

### 与 vLLM 的交互

两个系统不是严格竞争关系。2026 年 vLLM 添加了前缀缓存（`--enable-prefix-caching`）和缓存感知路由器（Rust 版 vLLM Router）。差距缩小但并未完全消失 — SGLang 的整个栈以基数树为核心；vLLM 是后来嫁接的。对于以前缀重用为主的工作负载，SGLang 仍是默认选择。对于没有强前缀模式的通用服务，vLLM 仍然相当或更好。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| RadixAttention | "SGLang 的那个" | KV 缓存索引为基数树，使共享前缀重用块 |
| 基数树 | "压缩前缀树" | 每个节点拥有一个 token 范围及其 KV 块的树 |
| 缓存感知调度器 | "热分支优先" | 优先服务共享驻留分支的请求的调度器 |
| 前缀缓存命中率 | "你的提示有多少是免费的" | 从重用 KV 块服务的提示 token 比例 |
| FCFS | "先来先服务" | 破坏前缀局部性的默认调度方式 |
| 分支级 LRU | "驱逐叶节点" | 匹配基数树形状的驱逐策略 |
| 提示模板排序 | "缓存键" | 提示的组件顺序决定了树能共享什么 |
| 系统提示固定 | "驻留前缀" | 保持不可变的系统部分固定以避免驱逐抖动 |
