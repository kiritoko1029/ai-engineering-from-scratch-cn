# AI SRE — 多智能体事故响应、运维手册与预测性检测

> AI SRE 通过 RAG 将 LLM 接入基础设施数据（日志、运维手册、服务拓扑），实现调查、文档化和协调阶段的自动化。2026 年的架构范式是多智能体编排——由主管智能体协调专业化智能体（日志、指标、运维手册）；AI 提出假设和查询，人类审批判断性决策。Datadog Bits AI 和 Azure SRE Agent 已将此作为托管产品推出。运维手册正在演进：NeuBird Hawkeye 采用对抗性评估（两个模型分析同一事故；一致 = 置信，分歧 = 不确定）；运维记忆在团队人员变动中持续保留。自动修复仍然保持谨慎：AI 建议，人类审批。完全自主的操作范围很窄（重启 Pod、回滚特定部署），并有严格的防护栏——任何兜售「一劳永逸」方案的人都在过度承诺。新兴前沿：事故前预测。MIT 研究报告称，基于历史日志、GPU 温度和 API 错误模式训练的 LLM 提前 10-15 分钟预测了 89% 的故障。预测：到 2026 年底，95% 的企业 LLM 将具备自动故障转移能力。

**类型：** 学习
**语言：** Python（标准库，玩具级多智能体事故分类模拟器）
**前置要求：** 阶段 17 · 13（可观测性），阶段 17 · 24（混沌工程）
**所需时间：** 约 60 分钟

## 学习目标

- 绘制多智能体 AI SRE 架构图：主管智能体 + 专业化智能体（日志、指标、运维手册）+ 人类审批关口。
- 解释为什么自动修复范围是窄的（重启 Pod、回滚部署）而非宽的（重新架构服务）。
- 说出对抗性评估模式（NeuBird Hawkeye）：两个模型一致 = 置信；分歧 = 升级处理。
- 引用 MIT 89% 早期检测结果及运营约束：没有执行能力的预测只是仪表盘。

## 问题所在

凌晨三点，值班工程师被呼叫通知唤醒。「结账错误率过高。」他们检查 Datadog、Loki、三份运维手册、部署日志。30 分钟后，他们才意识到根因是 KV 缓存激增导致的 vLLM OOM。他们重启了 Pod；错误消失。

在 2026 年，这 20 分钟的调查工作是可以自动化的。按服务聚合日志、关联最近部署、匹配运维手册——这些全部是 RAG + 工具调用。一个有监督的智能体可以在人类打开 Datadog 之前完成初步分类并提出假设。

完全自主的修复则是另一个问题。重启 Pod：安全。扩展 GPU 池：在策略允许范围内安全。重新架构服务：绝对不行。这门学科的核心在于划定那条窄线。

## 概念说明

### 多智能体架构

```
          Incident
             │
             ▼
        Supervisor
        /    |    \
       ▼     ▼     ▼
  Log agent  Metric agent  Runbook agent
       │     │     │
       └─────┴─────┘
             │
             ▼
        Hypothesis + evidence
             │
             ▼
        Human approval
             │
             ▼
        Action (narrow set)
```

主管智能体将事故分解为子查询。专业化智能体拥有工具访问权限（日志搜索、PromQL、文档检索）。主管智能体综合结果，向人类呈现假设 + 证据。人类审批或重新引导。

### 自动修复范围

**安全（窄范围）**：重启 Pod、回滚特定部署、在预批准范围内扩展资源池、启用预批准的功能开关。

**不安全（宽范围）**：更改服务拓扑、修改资源限制、部署新代码、更改 IAM 权限、变更数据库。

任何兜售「一劳永逸」方案的人都在过度承诺。随着 AI SRE 的成熟，安全集合会逐步扩大，但边界是真实存在的。

### 对抗性评估（NeuBird Hawkeye）

两个模型独立分析同一事故。如果它们对根因达成一致，则置信度高。如果存在分歧，则升级给人类处理，并同时展示两种假设。这是一个简单但有效的模式，能够过滤幻觉产生的根因。

### 运维记忆

团队人员流失是传统 SRE 的无声杀手——隐性知识随之离开。AI SRE 将运维手册和事后复盘存储在向量数据库中；智能体在每次新事故时进行检索。当新工程师加入时，AI 已经拥有完整的历史记录。

### 事故前预测

MIT 2025 年研究：基于历史日志、GPU 温度和 API 错误模式训练的 LLM 在测试集上提前 10-15 分钟预测了 89% 的故障。

现实检验：没有执行能力的预测只是仪表盘。运营问题是「当我们预测到故障时，我们该做什么？」预先排空？呼叫通知？自动扩展？答案取决于具体策略。

### 2026 年产品

- **Datadog Bits AI** — Datadog 内置的托管 SRE 副驾驶。
- **Azure SRE Agent** — Azure 原生方案。
- **NeuBird Hawkeye** — 对抗性评估 + 运维记忆。
- **PagerDuty AIOps** — 分类 + 去重。
- **Incident.io Autopilot** — 事故指挥官 + 协调。

### 运维手册即代码

运维手册从 Confluence 页面演进为带结构化章节（症状、假设、验证、操作）的版本化 Markdown。结构化运维手册能为 RAG 检索提供更好的结果。在启动任何 AI SRE 推广时，首先将非结构化运维手册转化为结构化格式。

### 关键数字

- MIT 早期检测：89% 的故障，提前 10-15 分钟。
- 多智能体分类：主管智能体 +（日志、指标、运维手册）+ 人类。
- 安全自动修复集合：重启 Pod、回滚部署、在范围内扩展。
- 对抗性评估：两个模型独立运行；一致 = 置信。

## 练习

1. 运行 `code/main.py`。如果日志和指标智能体产生分歧怎么办？主管智能体如何解决？
2. 为你的服务定义三个「安全」的自动修复操作。逐一说明理由。
3. 编写一个结构化运维手册模板：章节、必填字段、验证命令。
4. 预测性检测在提前 12 分钟时触发。你的策略是什么——呼叫通知、预先排空，还是两者兼有？
5. 论证 3 人团队是否应该在 2026 年采用 AI SRE 还是等待。考虑成熟度、事故量和风险。
