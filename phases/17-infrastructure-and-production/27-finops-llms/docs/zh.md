# 面向 LLM 的 FinOps — 单位经济学与多租户归因

> 传统 FinOps 在面对 LLM 支出时会失效。成本核算的基本单位是 token 交易，而非资源运行时间。标签体系不再适用——一次 API 调用是一笔交易，而非一项资产。工程决策（prompt 设计、上下文窗口、输出长度）本质上就是财务决策。2026 年的最佳实践包含三个归因维度，应在上线第一天就完成埋点：按用户（`user_id`）用于席位定价和扩展，按任务（`task_id` + `route`）用于产品功能层面的成本核算和优先级排序，按租户（`tenant_id`）用于单位经济学和续费决策。四个 token 层——prompt、工具、记忆、响应——合并为单一账单会掩盖真实支出。多租户产品的强制执行阶梯：每租户速率限制（预期峰值的 2-3 倍，返回 429 + `Retry-After`）；每日支出上限（合同上限的 1.5-3 倍；触发速率收紧 + 告警）；当支出 z-score > 4 时启动熔断开关（自动暂停 + 呼叫值班）。归因模式：标签聚合、遥测关联（trace-ID → 计费；准确率最高）、采样推断、模型分配、事件溯源、实时流式处理。单位度量指标：每个已解决查询的成本、每个已生成产出物的成本——而非每百万 token 成本。事后补标签总有遗漏；应在请求创建时就完成埋点。

**类型：** 学习
**语言：** Python（标准库，带熔断开关的简易成本归因模拟器）
**前置要求：** Phase 17 · 13（可观测性），Phase 17 · 14（缓存）
**所需时间：** 约 60 分钟

## 学习目标

- 解释传统 FinOps（标签 + 分层）为何在 LLM 支出上失效，并列举三个新的归因维度。
- 列举四个 token 层（prompt、工具、记忆、响应），说明为何单桶计费会掩盖成本。
- 为多租户产品设计强制执行阶梯（速率限制 → 支出上限 → 熔断开关）。
- 选择单位度量指标（每个已解决查询/产出物的成本），而非 $/百万 token。

## 问题所在

你的账单显示 $40,000。你不知道：
- 哪个租户花了这笔钱。
- 哪个产品功能驱动了这笔支出。
- 是否有单个用户存在滥用行为。
- prompt 膨胀、工具调用还是记忆放大才是罪魁祸首。

在云服务提供商侧做标签聚合适用于云资源（EC2、S3），因为标签会传播到账单行项目。LLM API 调用不会自动打标签——你必须在调用处手动附加 user/task/tenant 信息并贯穿传递。事后归因总有遗漏。

## 概念说明

### 三个归因维度

**按用户**（`user_id`）：谁花了多少钱。驱动席位定价、扩展对话，识别重度用户。

**按任务**（`task_id` + `route`）：哪个产品功能花了多少钱。驱动功能优先级排序、砍掉高成本功能的决策。

**按租户**（`tenant_id`）：哪个客户是盈利的。驱动单位经济学、续费定价、分层阈值。

在上线第一天就在调用处完成三个维度的埋点。事后补救总是更差。

### 四个 token 层

| 层 | 示例 | 典型占比 |
|-------|---------|---------------------|
| Prompt | 系统 + 用户输入 | 40-60% |
| 工具 | 工具调用结果回传 | 20-40%（代理工作负载） |
| 记忆 | 历史对话 / 检索到的文档 | 10-30% |
| 响应 | 模型输出 | 10-30% |

将四层合并计费会让优化无从下手。在归因方案中将它们拆开。

### 强制执行阶梯

1. **速率限制**，按租户设定。预期峰值的 2-3 倍。返回 429 并附带 `Retry-After`。租户会感受到一些摩擦；但不会有意外账单。

2. **每日支出上限**，按租户设定。合同上限的 1.5-3 倍。触发条件：收紧速率限制 + 通知客户成功团队。

3. **熔断开关**，当支出 z-score 相对于租户基线超过 4 时触发。自动暂停租户；呼叫值班；升级到运维和客户成功团队。

### 归因模式

- **标签聚合**：附加元数据头；后续聚合。简单；粗略。
- **遥测关联**：通过 trace ID 将链路追踪数据关联到计费系统。准确率最高。成熟团队的做法。
- **采样 + 推断**：采样 5-10%，乘以倍数。对于粗略支出估算有成本效益；会遗漏异常值。
- **模型分配**：回归分析推断成本驱动因素。适用于没有标签的历史数据。
- **事件溯源**：将成本作为流中的事件（Kafka / Kinesis）。实时性好。
- **实时流式处理**：亚秒级仪表盘更新。

### 每 X 成本才是单位度量指标

$/百万 token 是供应商话术。产品指标应该是：

- 每个已解决支持工单的成本。
- 每篇已生成文章的成本。
- 每个成功代理任务的成本。
- 每用户会话分钟的成本。

将成本与产品成果挂钩。否则优化就缺乏锚点。

### 成本归因 trace 结构

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次调用都输出。存储在数据湖中。按维度聚合。Phase 17 · 13 的可观测性栈就是这些数据的归属。

### 复合节省栈

叠加：缓存 + 批处理 + 路由 + 网关。四者叠加时：
- L2 缓存（Phase 17 · 14）：输入成本降低约 10 倍。
- 批处理（Phase 17 · 15）：50% 折扣。
- 路由到更便宜的模型（Phase 17 · 16）：成本降低 60%。
- 网关效率（Phase 17 · 19）：冗余 + 重试。

最佳情况叠加：约为朴素基线的 5-10%。大多数团队启用了 2-3 个杠杆；很少有团队能同时叠加全部四个。

### 你应该记住的数字

- 归因维度：按用户、按任务、按租户。
- 四个 token 层：prompt、工具、记忆、响应。
- 熔断开关：支出 z-score > 4。
- 单位度量指标：每个已解决查询的成本，而非 $/百万 token。
- 叠加优化：约为基线的 5-10% 是可能的。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------------|------------------------|
| 按用户归因 | "用户级成本" | 每次调用附加 `user_id` |
| 按任务归因 | "功能成本" | `task_id` + `route` 标识产品功能面 |
| 按租户归因 | "客户成本" | `tenant_id`；驱动单位经济学 |
| 四个 token 层 | "成本层" | prompt + 工具 + 记忆 + 响应 |
| 速率限制 | "429 防护" | 网关层按租户强制执行的上限 |
| 每日支出上限 | "每日上限" | 租户级预算，附带告警 |
| 熔断开关 | "自动暂停" | 支出 z-score > 4 触发自动挂起 |
| 每解决成本 | "产品单位指标" | 成本与产品成果挂钩，而非与 token 挂钩 |
| 遥测关联 | "trace 到计费" | 准确率最高的归因模式 |
| 叠加优化 | "缓存+批处理+路由+网关" | 复合节省至基线的约 5-10% |
