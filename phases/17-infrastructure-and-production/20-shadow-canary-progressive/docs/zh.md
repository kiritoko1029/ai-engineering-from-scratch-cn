# LLM 的影子流量、金丝雀发布与渐进式部署

> LLM 的发布部署综合了软件部署中最困难的部分：没有单元测试、故障模式分散、信号延迟。其流程为：（1）影子模式——将生产请求复制到候选模型，记录日志并对比，对用户零影响；能发现明显的分布问题，但不能保证质量；（2）金丝雀发布——渐进式流量切换 10% → 25% → 50% → 75% → 100%，每一步都设有准入门控；跟踪延迟百分位数、每次请求成本、错误/拒绝率、输出长度分布、用户反馈率；（3）在稳定性确认后进行 A/B 测试以比较不同方案。非确定性不可消除——由于 GPU 浮点运算的非结合性以及批次大小差异，即使输入完全相同，准确率在不同运行之间也可能存在高达 15% 的波动。成本是变量而非常量——一个提升 20% 的模型每次调用的成本可能是原来的 3 倍。回滚速度是决定性因素：如果回滚需要重新部署，那就太慢了。策略由配置/功能标志控制；模型存储在注册中心并使用固定的摘要标识；回滚 = 切换策略 + 恢复阈值 + 锁定旧模型，以秒计。

**类型：** 学习
**语言：** Python（标准库，金丝雀渐进模拟器演示）
**前置要求：** 第 17 阶段 · 第 13 课（可观测性），第 17 阶段 · 第 21 课（A/B 测试）
**所需时间：** 约 60 分钟

## 学习目标

- 区分影子模式（零影响对比）、金丝雀发布（线上流量渐进切换）和 A/B 测试（稳定性确认后的对比）。
- 列举五项 LLM 特有的金丝雀指标（延迟、每次请求成本、错误/拒绝率、输出长度分布、用户反馈）。
- 解释 LLM 的非确定性（高达 15%）如何改变发布中"稳定"的含义。
- 设计一个以秒计的回滚路径（策略切换），而非以小时计（重新部署）。

## 问题所在

你发布了一个新模型。离线评估显示准确率提升了 3%。你在生产环境中启用了它。24 小时内，成本上涨了 40%，用户踩赞率上升了 8%，三个客户工单报告"回答很奇怪"。你执行回滚，重新部署花了 3 小时。你的周末泡汤了。

上述每一个问题都是可以避免的。影子模式会在任何用户看到之前就发现 40% 的成本飙升。金丝雀发布会在踩赞率上升时停在 10% 阶段。策略标志回滚只需 30 秒。这种规范化的流程正是填补"离线评估看起来不错"和"真实用户满意"之间鸿沟的关键。

## 概念说明

### 影子模式

候选模型接收与生产模型相同的请求；输出被记录但不返回给用户。对用户零影响。记录内容包括：

- 输出内容（与生产模型的差异对比）。
- Token 数量（成本差异）。
- 延迟。
- 拒绝和错误。

能发现的问题：成本暴涨、长度回退、明显的拒绝率变化、硬性错误。不能发现的问题：用户能感知的质量差异。影子模式是一种冒烟测试，而非质量测试。

### 金丝雀发布

带准入门控的渐进式流量切换。典型进度：1% → 10% → 25% → 50% → 75% → 100%。每一步对 5 项指标进行门控检查：

1. **延迟百分位数** —— P50、P95、P99。触发条件：金丝雀的 P99 > 基线的 1.5 倍。
2. **每次请求成本** —— 综合费用。触发条件：高于基线 20% 以上。
3. **错误/拒绝率** —— 5xx 错误加上显式拒绝。触发条件：基线的 2 倍。
4. **输出长度分布** —— 均值 + P99。触发条件：分布发生偏移。
5. **用户反馈率** —— 踩赞数/工单提交数。触发条件：基线的 1.5 倍。

### 非确定性是新的方差来源

相同的输入会产生不完全相同的输出。原因包括：

- GPU 浮点运算的非结合性（浮点归约顺序因批次不同而变化）。
- 批次大小差异（同一条提示在 128 个批次与 16 个批次中的表现不同）。
- 采样（温度 > 0）。

实测结果：在相同的评估集上，不同运行之间的准确率差异高达 15%。发布中的"稳定"意味着指标在预期方差范围内，而非与基线完全一致。门控阈值应设置在噪声底线之上。

### 成本是变量

一个提升 20% 的模型每次调用的成本可能是原来的 3 倍。每次请求成本是五项门控指标之一。发布一个破坏单位经济效益的"更好"模型，就是需要回滚的场景。

### 回滚是你的武器

- 策略标志（功能标志系统）：在配置中切换百分比；以秒计。
- 模型锁定（注册中心摘要）：锁定的模型不会自动升级。
- 回滚 = 恢复标志 + 将锁定摘要设为上一版本。以秒计，而非以小时计。

如果你的技术栈回滚需要重新部署，请在上线前解决这个问题。

### 工具链

**Argo Rollouts** / **Flagger** —— Kubernetes 渐进式发布控制器。与 Istio/Linkerd 的加权路由集成。

**Istio 加权路由** —— 服务网格级别的流量分割。

**KServe / Seldon Core** —— 内置金丝雀发布能力的模型服务。

**功能标志** —— LaunchDarkly、Flagsmith、Unleash。策略层面的切换，无需重新部署。

### 指标检查频率

金丝雀门控每 5 到 15 分钟检查一次，具体取决于流量规模。1% 的流量、每分钟 10 个请求，每个窗口可获得 50 到 150 个数据点——对延迟来说足够，但对用户反馈来说噪声较大。10% 的流量可提供约 10 倍的数据量。每一步的进度应暂停足够长的时间，以积累足够的样本量。

### A/B 测试步骤是可选的

如果新模型有明显不同的行为（不同的行为模式、不同的成本曲线、不同的风格），在金丝雀通过后，可在 50% 流量下进行 A/B 测试。如果只是改进版本，在金丝雀门控通过后直接推进到 100%。

### 你应该记住的数字

- 金丝雀进度：1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性上限：在相同输入上，不同运行之间的方差高达 15%。
- 五项金丝雀指标：延迟、成本、错误/拒绝率、输出长度、用户反馈。
- 成本门控：高于基线 20% 以上即触发。
- 回滚：以秒计，而非以小时计。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| 影子模式 | "复制到新模型" | 零影响地将请求发送到候选模型进行记录 |
| 金丝雀发布 | "渐进式流量切换" | 带门控的逐步暴露给用户的发布方式 |
| 准入门控 | "发布检查" | 阻止进度推进的指标阈值 |
| 非确定性 | "LLM 方差" | 不可消除的运行间差异 |
| 策略标志 | "标志切换回滚" | 配置层面的回滚，以秒计而非以小时计 |
| 模型锁定 | "注册中心摘要" | 对模型版本的不可变引用 |
| Argo Rollouts | "K8s 渐进式发布" | Kubernetes 原生的金丝雀/回滚控制器 |
| KServe | "推理 K8s" | 具备金丝雀发布原语的模型服务 |
| Istio 加权路由 | "网格分流" | 服务网格流量分割器 |
