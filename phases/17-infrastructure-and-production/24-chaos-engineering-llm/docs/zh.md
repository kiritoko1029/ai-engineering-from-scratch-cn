# LLM 生产环境的混沌工程

> LLM 的混沌工程在 2026 年已成为一门独立学科。在生产环境中运行实验前，需满足以下前提条件：已定义的 SLI/SLO、trace+metric+log 可观测性、自动化回滚、运行手册、值班人员。架构分为四个平面：控制平面（实验调度器）、目标平面（服务、基础设施、数据存储）、安全平面（防护机制 + 中止 + 流量过滤）、可观测平面（指标 + 链路追踪 + 日志）、反馈平面（用于 SLO 调整）。防护机制是必需的：当每日错误预算消耗超过预期的 2 倍时，消耗速率告警会暂停实验；抑制窗口 + 连接 ID 关联可以减少告警噪音。实验节奏：每周进行小型金丝雀测试 + SLO 审查；每月进行游戏日 + 复盘；每季度进行跨团队弹性审计 + 依赖关系映射。LLM 特定实验包括：内存过载、网络故障、提供商中断、格式错误的提示词、KV 缓存驱逐风暴。工具包括：Harness 混沌工程（LLM 驱动的建议、爆炸半径缩小、MCP 工具集成）；LitmusChaos（CNCF）；Chaos Mesh（CNCF Kubernetes 原生）。

**类型：** 学习
**语言：** Python（标准库，简易混沌实验运行器）
**前置要求：** Phase 17 · 23（AI 的 SRE），Phase 17 · 13（可观测性）
**所需时间：** 约 60 分钟

## 学习目标

- 列举混沌工程的五个前提条件（SLI/SLO、可观测性、回滚、运行手册、值班），并解释为什么跳过任何一项都会破坏实践。
- 绘制四个平面（控制、目标、安全、可观测）及反馈循环至 SLO 的示意图。
- 列举五个 LLM 特定实验（内存过载、网络故障、提供商中断、格式错误提示词、KV 驱逐风暴）。
- 根据技术栈选择工具——Harness、LitmusChaos、Chaos Mesh。

## 问题所在

传统技术栈中的混沌测试已经成熟。LLM 技术栈引入了新的故障模式。一个包含 4K token 的提示词，如果含有恶意字符，会导致分词器卡住 12 秒。上游提供商返回 429 状态码；网关重试；重试导致并发放大，最终服务发生 OOM（内存溢出）。突发负载下的 KV 缓存驱逐风暴会引发重填充级联，使计算资源饱和。

这些故障在单元测试中都无法发现。混沌工程就是让你在用户之前发现这些问题的方法。

## 概念说明

### 前提条件

不要在没有以下条件的情况下在生产环境中运行混沌实验：

1. **SLI/SLO** ——已定义的服务级别指标和目标。
2. **可观测性** ——链路追踪、指标、日志，已接入仪表盘。
3. **自动化回滚** ——Phase 17 · 20 策略标志回滚。
4. **运行手册** ——结构化文档，参见 Phase 17 · 23。
5. **值班人员** ——负责响应的人。

缺少任何一项，混沌就会变成真实事故。

### 四个平面 + 反馈

**控制平面** ——实验调度器（Litmus 工作流、Chaos Mesh 调度、Harness UI）。

**目标平面** ——服务、Pod、节点、负载均衡器、数据存储。

**安全平面** ——紧急停止开关、抑制窗口、爆炸半径限制、错误预算门控。

**可观测平面** ——常规指标 + 连接 ID 关联，以区分混沌引发的故障与自然故障。

**反馈循环** ——实验发现反馈到 SLO 调整、运行手册更新、代码修复。

### 防护机制是必需的

- **消耗速率告警**：当每日错误预算消耗超过预期的 2 倍时，暂停实验。
- **抑制窗口**：在实验期间，静默爆炸半径内的非实验告警。
- **连接 ID 关联**：所有实验引发的错误都带有标签，以便值班人员去重。

### 五个 LLM 特定实验

1. **内存过载** ——通过高并发发送长上下文请求，强制触发 KV 缓存抢占风暴。观察：服务是优雅降级还是崩溃？

2. **网络故障** ——切断推理网关与提供商之间的连接。观察：备用方案是否在 SLA 内生效？（Phase 17 · 19）

3. **提供商中断模拟** ——OpenAI 返回 100% 429。观察：路由是否切换到 Anthropic？（Phase 17 · 16, 19）

4. **格式错误提示词** ——注入导致分词器卡住的负载（例如，深度嵌套的 unicode、巨大的 UTF-8 码点）。观察：单个请求是否会锁定工作进程？

5. **KV 驱逐风暴** ——通过使 vLLM 块预算饱和来强制驱逐。观察：LMCache 是否能恢复，还是服务降级？

### 实验节奏

- **每周** ——在预发布环境进行小型金丝雀实验，可能在生产环境进行 5% 的测试。
- **每月** ——针对特定场景安排游戏日；跨团队参与；事后复盘。
- **每季度** ——跨团队弹性审计；依赖关系图更新。

### 工具

- **Harness 混沌工程** ——商业产品；AI 驱动的实验建议；爆炸半径缩小；MCP 工具集成。
- **LitmusChaos** ——CNCF 毕业项目；基于 Kubernetes 工作流。
- **Chaos Mesh** ——CNCF 沙箱项目；Kubernetes 原生 CRD 风格。
- **Gremlin** ——商业产品；广泛支持。
- **AWS FIS** / **Azure Chaos Studio** ——托管云服务。

### 从小处开始

第一个实验：在稳定流量下终止一个解码副本的 Pod。观察路由重定向和恢复。如果这一步成功且看起来安全，再升级到网络混沌实验。

第一个 LLM 特定实验：注入一个提供商 429 错误，持续 5 分钟。观察备用方案。大多数团队会发现他们的备用方案并没有被充分测试。

### 需要记住的数字

- 四个平面：控制、目标、安全、可观测。
- 消耗速率暂停：每日预算消耗的 2 倍。
- 实验节奏：每周金丝雀，每月游戏日，每季度审计。
- 五个 LLM 实验：内存、网络、提供商、格式错误提示词、KV 风暴。
