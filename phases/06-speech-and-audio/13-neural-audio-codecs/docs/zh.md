# 神经网络音频编解码器——EnCodec、SNAC、Mimi、DAC以及语义-声学分离技术

> 到 2026 年，音频生成几乎完全依赖于令牌。EnCodec、SNAC、Mimi 和 DAC 等技术会将连续波形转换为变换器能够预测的离散序列。将语义信息与声学信息分开处理——将第一个码本视为语义部分，其余部分视为声学部分——这是自 Transformer 出现以来音频领域最重要的架构变革。

**类型：** 学习
**语言：** Python
**先修知识：** 第 6 阶段 · 02（频谱图）、第 10 阶段 · 11（量化）、第 5 阶段 · 19（子词分词）
**时长：** 约 60 分钟

## 问题所在

语言模型基于离散的标记进行工作，而音频则是连续的。若希望为语音/音乐构建类似大语言模型的系统——如 MusicGen、Moshi、Sesame CSM、VibeVoice、Orpheus——首先需要一种**神经音频编解码器**：即一个经过训练的编码器，能够将音频离散化为少量标记；以及一个对应的解码器，用于重构波形。

目前主要存在两大类编解码器：

1. **以重建优先为目标的编解码器**——如 EnCodec、DAC。这类编解码器的优化目标是提升听觉质量。其使用的标记属于“声学标记”，能够捕捉包括扬声器特性、音色、背景噪声在内的所有信息。
2. **以语义优先为目标的编解码器**——如 Mimi（Kyutai）、SpeechTokenizer。这类编解码器要求第一个代码本用于编码语言/语音内容（通常通过从 WavLM 中提取信息实现），后续的代码本则负责处理声学细节。

2024–2026 年间的研究发现：**纯重建型编解码器在尝试根据文本生成语音时会导致输出模糊不清**。因为大语言模型需要在同一个代码本中同时学习语言结构与声学结构，这种方式难以实现规模化扩展。通过将两者分离——即使用第 0 个语义代码本，以及第 1–N 个声学代码本——才使得 Moshi 和 Sesame CSM 能够正常运行。

## 概念概述

![四种编解码器对比：EnCodec、DAC、SNAC（多尺度）、Mimi（语义+声学）](../assets/codec-comparison.svg)

### 核心技巧：残差向量量化（RVQ）

与需要数百万个码字才能保证高质量的单个大代码本不同，所有现代音频编解码器均采用**RVQ**技术：即由多个小型代码本级联构成的结构。第一个代码本对编码器输出进行量化，第二个代码本对残差值进行量化，以此类推。每个代码本包含1024个码字。8个代码本组合后的有效词汇量即为1024^8 = 10^24。

在解码阶段，解码器会累加每一帧中所有被选中的码字，从而重建音频信号。

### 2026年至关重要的四种编码解码器

**EnCodec（Meta，2022年）**。基准模型。基于波形形式的编解码器，采用RVQ瓶颈结构。支持24 kHz采样率，可配置32组代码本，默认使用4组代码本，编码率为1.5 kbps。采用`1D卷积 + 变换器 + 1D卷积`的架构，被MusicGen所采用。

**DAC（Descript，2023年）**。基于RVQ技术，其代码本经过L2归一化处理，并使用周期性激活函数以及改进的损失函数。在所有开源编解码器中具有最高的重建保真度——当使用12组代码本时，其输出语音有时与原始语音难以区分。支持44.1 kHz全频段。

**SNAC（Hubert Siuzdak，2024年）**。多尺度RVQ模型——粗略级别的代码本以低于精细级别代码本的帧率运行。该模型能够对音频进行分层建模：首先生成约12 Hz频率的粗略“草图”，再补充50 Hz频率的细节信息。由于其分层结构与基于语言模型的生成方式高度契合，因此被Orpheus-3B所采用。

**Mimi（Kyutai，2024年）**。堪称2026年的颠覆性技术。帧率为12.5 Hz（极低），配备8组代码本，编码率为4.4 kbps。其中代码本0是**从WavLM中提取并优化而来的**——经过训练以预测WavLM的语音内容特征；代码本1至7则为声学残差。这种结构为Moshi（第15课）及Sesame CSM提供了技术基础。

### 帧率对语言建模而言至关重要

帧率越低 = 序列长度越短 = 大语言模型推理速度越快。

| 编码器 | 帧率 | 1秒 = N帧 | 适用场景 |
|-------|-----------|----------------|---------|
| EnCodec-24k | 75 Hz | 75 | 音乐、普通音频 |
| DAC-44.1k | 86 Hz | 86 | 高保真音乐 |
| SNAC-24k（粗粒度） | ~12 Hz | 12 | 适用于AR场景的大语言模型 |
| Mimi | 12.5 Hz | 12.5 | 流式语音 |

在12.5 Hz的帧率下，10秒的语音内容仅包含125帧编码数据——Transformer模型可以轻松完成预测。

### 语义标记与声学标记

```
frame_t → [semantic_token_t, acoustic_token_0_t, acoustic_token_1_t, ..., acoustic_token_6_t]
```

- **语义标记（Mimi中的代码本0）**。用于编码所表达的内容——音素、单词及文本内容。该模型通过辅助预测损失函数从WavLM中提取而来。
- **声学标记（代码本1-7）**。用于编码音色、说话人身份、语调以及背景噪声等细节信息。

自回归语言模型首先根据文本条件预测语义标记，随后再根据语义标记及说话人参考信息预测声学标记。正是这种分解方式使得现代文本转语音技术能够实现无样本声音克隆：语义模型负责处理内容，而声学模型则负责处理音色。

### 2026年重建质量（比特/秒，比特率越低越好）

| 编码器 | 比特率 | PESQ值 | ViSQOL值 |
|-------|---------|------|--------|
| Opus-20kbps | 20 kbps | 4.0 | 4.3 |
| EnCodec-6kbps | 6 kbps | 3.2 | 3.8 |
| DAC-6kbps | 6 kbps | 3.5 | 4.0 |
| SNAC-3kbps | 3 kbps | 3.3 | 3.8 |
| Mimi-4.4kbps | 4.4 kbps | 3.1 | 3.7 |

像 Opus 这样的传统编码器在每比特的感知质量方面仍具有优势。而神经网络编码器则在**离散标记**（Opus 不生成此类标记）以及**生成模型质量**（语言模型能够利用这些标记实现的功能）方面更具优势。

## 构建它

### 步骤 1：使用 EnCodec 进行编码

```python
from encodec import EncodecModel
import torch

model = EncodecModel.encodec_model_24khz()
model.set_target_bandwidth(6.0)  # kbps

wav = torch.randn(1, 1, 24000)
with torch.no_grad():
    encoded = model.encode(wav)
codes, scale = encoded[0]
# codes: (1, n_codebooks, n_frames), dtype=int64
```

在 6 kbps 速率下，`n_codebooks=8`。每个码值的范围为 0-1023（10 位）。

### 步骤 2：解码并测量重建结果

```python
with torch.no_grad():
    wav_recon = model.decode([(codes, scale)])

from torchaudio.functional import compute_deltas
import torch.nn.functional as F

mse = F.mse_loss(wav_recon[:, :, :wav.shape[-1]], wav).item()
```

### 步骤 3：语义-声学分离（Mimi 风格）

```python
from moshi.models import loaders
mimi = loaders.get_mimi()

with torch.no_grad():
    codes = mimi.encode(wav)  # shape (1, 8, frames@12.5Hz)

semantic = codes[:, 0]
acoustic = codes[:, 1:]
```

语义代码本 0 已与 WavLM 对齐。您可以训练一个文本到语义的变换器——其词汇量远小于直接处理音频的方案。随后，再使用独立的声学到波形解码器，并以扬声器参考作为条件输入。

### 步骤 4：为何选择 AR LM 而非编解码器令牌

对于使用 Mimi 的 12.5 Hz × 8 代码本的 10 秒语音片段：

```
N_tokens = 10 * 12.5 * 8 = 1000 tokens
```

对于Transformer模型而言，1000个token的上下文长度属于极小的规模。一个拥有256百万参数的Transformer模型，在现代GPU上仅需几毫秒即可生成10秒钟的语音内容。

## 使用它

问题映射 → 编码器：

| 任务 | 编码器 |
|------|-------|
| 通用音乐生成 | EnCodec-24k |
| 最高保真度重建 | DAC-44.1k |
| 基于语音的 AR 大语言模型（TTS） | SNAC 或 Mimi |
| 全双工语音流传输 | Mimi（12.5 Hz） |
| 带文本的声音效果库 | EnCodec + T5 条件编码 |
| 高精度音频编辑 | DAC + 修复技术 |

经验法则：**若构建生成模型，优先选用 Mimi 或 SNAC；若构建压缩流程，则使用 Opus。**

## 常见陷阱

- **代码本数量过多。** 增加代码本会线性提升保真度，但也会同步增加语言模型序列的长度。建议控制在 8-12 个即可。
- **帧率不匹配。** 先在 12.5 Hz 的 Mimi 上训练语言模型，再在 50 Hz 的 EnCodec 上进行微调时，会导致系统无声失败。
- **假设所有代码本的作用相同。** 在 Mimi 中，代码本 0 包含核心内容；若丢失该代码本，会严重影响可理解性，而丢失代码本 7 几乎不会造成明显影响。
- **仅以重建质量作为评估指标。** 即使编解码器的重建效果很好，但如果其语义结构较差，对于基于语言模型的生成任务而言依然毫无用处。

## 练习题

1. **简单。** 运行 `code/main.py`。该脚本实现了一个简易的标量+残差量化器，并在添加码本时测量重建误差。
2. **中等难度。** 安装 `encodec`，并在保留的语音片段上对比 1、4、8、32 个码本的性能。绘制 PESQ 或 MSE 随比特率的变化曲线。
3. **高难度。** 加载 Mimi 数据集。对一段音频进行编码。将码本 0 替换为随机整数后再解码；接着以相同方式处理码本 7。比较两种情况下的失真情况——码本 0 的失真应导致语音完全无法理解；而码本 7 的失真则几乎不会改变任何内容。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| RVQ | 残差量化 | 由多个小型代码本级联组成；每个代码本对前一个残差进行量化。 |
| 帧率 | 编解码器速度 | 每秒的 token-frame 数量。数值越低表示语言模型运行速度越快。 |
| 语义代码本 | 代码本 0（Mimi） | 从 SSL 特征中提取的代码本，用于编码内容信息。 |
| 声学代码本 | 其他所有代码本 | 负责处理音色、韵律、噪声及细微细节。 |
| PESQ / ViSQOL | 感知质量 | 与 MOS 相关的客观评估指标。 |
| EnCodec | 元编解码器 | RVQ 的基准实现；被 MusicGen 所采用。 |
| Mimi | Kyutai 编解码器 | 帧率为 12.5 Hz，采用语义-声学分离架构，为 Moshi 提供支持。 |
