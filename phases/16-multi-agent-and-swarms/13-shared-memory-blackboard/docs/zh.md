# 共享记忆与黑板模式

> 2026 年的多智能体系统中并存着两种方法：**消息池**（每个人都能看到每个人的消息，如 AutoGen GroupChat 或 MetaGPT）和**带订阅的黑板**（智能体订阅相关事件，如 Context-Aware MCP 或 Matrix 框架）。两者都是多智能体系统中唯一的有状态部分 —— 这意味着两者都是有趣 bug 产生的地方。典型的失败模式是**记忆投毒**：一个智能体产生幻觉写入一条"事实"，其他智能体将其视为已验证，准确度逐渐下降，而这种方式比立即崩溃更难调试。本课从标准库构建这两种结构，注入一次投毒攻击，并展示在生产中真正有效的三种缓解措施。

**类型：** 学习 + 构建
**语言：** Python（标准库、`threading`）
**前置要求：** 第 16 阶段 · 04（原始模型），第 16 阶段 · 09（并行群体网络）
**所需时间：** 约 75 分钟

## 问题

多智能体系统需要一个地方让智能体共享事实。一个直接的选项是"在消息中传递所有内容" —— 但这相当于用额外的复制重新发明共享状态。另一个是"给每个人一个全局日志" —— 但全局日志无限制增长且容易被投毒。第三个是"为每个智能体投影视图" —— 可扩展但模式设计复杂。

当其中一个智能体产生幻觉并将其写入共享状态时，每个读取该状态的下游智能体都会将幻觉采纳为事实。当人类注意到时，推理链已经深入五步，根本原因是第三条写入的消息。调试多智能体的准确度衰减比调试崩溃更难。

这就是记忆投毒。它是 MAST 分类法（Cemri 等人，arXiv:2503.13657）中记录第二多的失败类别，而且它是结构性的：任何没有来源追溯和不可写验证器的共享记忆设计最终都会出现这个问题。

## 概念

### 两种主要拓扑

**完整消息池。** 每个智能体读取每条消息。AutoGen GroupChat 和 MetaGPT 使用这种模式。简单、透明、可检查，但不能扩展到超过约 10 个智能体，因为每个智能体的上下文会被其他智能体的工作填满。

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**带订阅的黑板。** 智能体声明对主题的兴趣；底层只路由相关消息。CA-MCP（arXiv:2601.11595）和 Matrix 去中心化框架（arXiv:2511.21686）使用这种模式。可扩展性更好，但需要预先进行模式设计以使订阅有意义。

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### 各自的适用场景

- **完整消息池**在智能体数量少（< 10）、异构、对话时间短时胜出。当每个人都能看到所有内容时，推理谁说了什么非常简单。
- **黑板**在智能体数量多、角色同质但实例众多（群体）、对话长时间运行时胜出。路由节省 token 成本并减少上下文污染。

生产系统通常混合使用：顶层是一个小型完整消息池（规划层），下层是黑板（工作层）。

### 记忆投毒，一个场景

三个智能体处理一个研究任务。智能体 A 是检索智能体。智能体 B 是摘要智能体。智能体 C 是分析智能体。

1. A 获取了一个页面并向共享状态写入一条消息："该研究报告准确率提升了 42%。"
2. 获取的页面实际上说的是"提升了 4.2%"。A 幻觉了一个小数点。
3. B 读取共享状态后写入："报告了大幅 42% 准确率提升（来源：A）。"
4. C 读取共享状态后写入："建议采用 —— 42% 的提升是变革性的。"
5. 最终报告引用了一个从未存在过的 42% 数字。

没有智能体崩溃。没有测试失败。系统"正常工作"。幻觉通过共享状态从一个智能体的上下文传播到了每个下游智能体的推理中。

### 为什么这是结构性的

没有共享状态时，智能体 A 的幻觉留在 A 的上下文中。下游智能体会重新获取或重新推导，可能会发现错误。有了朴素的共享状态，A 的上下文变成了每个人的上下文，幻觉被洗白成了事实。

问题不在于共享状态本身 —— 而在于**没有来源追溯且没有独立验证器**的共享状态。三种缓解措施可以解决这个问题：

1. **在每次写入时记录来源。** 共享状态中的每个条目记录谁写的、什么时候写的、在什么提示词下写的，以及（如适用）智能体引用了什么来源。下游智能体根据来源可信度持怀疑态度读取。
2. **版本化写入；将它们视为仅追加。** 修正是一条取代旧条目的新条目，而不是就地更新。审计追踪得以保留。
3. **至少保留一个不能写入共享状态的智能体。** 一个只读的验证器智能体采样条目、重新获取来源，并标记不一致之处。因为它不能写入池中，所以不会被池投毒。

### 黑板先例（Hayes-Roth，1985）

黑板模式比 LLM 智能体早了四十年。Hayes-Roth（1985，"A Blackboard Architecture for Control"）描述了专家知识源（Knowledge Sources）观察全局黑板、贡献部分解决方案并触发其他知识源的模式。2026 年的黑板（CA-MCP、Matrix）是相同的模式，只是 LLM 智能体作为知识源，JSON 块作为部分解决方案。旧文献中已经记录了写入竞争、机会控制和一致性的解决方案，而现代系统正在重新发现这些。

### 投影视图与完整视图

纯黑板给每个订阅者相同的投影视图（主题范围）。更激进的设计是**按智能体投影视图**：每个智能体获得根据其角色定制的视图。LangGraph 的状态归约器是 2026 年的典型实现 —— 归约器函数将全局状态折叠为特定角色的切片。

按智能体投影视图可扩展性更好，但需要模式。没有模式，你就在每个智能体的提示词中重建临时投影。

### 写入竞争模式

多个智能体同时写入是一个并发问题，而不仅仅是 LLM 问题。三种模式有效：

- **顺序写入者（单一生产者）。** 所有写入通过一个协调者智能体进行序列化。简单，但有瓶颈。
- **带版本控制的乐观并发。** 每个条目都有版本；写入者在版本不匹配时失败并重试。经典的数据库技术。
- **主题分区。** 不同智能体拥有不同的主题。没有跨主题竞争。需要设计分区边界。

大多数 2026 年的框架默认使用顺序写入者，因为 LLM 调用足够慢，竞争很少见，瓶颈不会造成太大影响。

### 不可写验证器

最具承载力的缓解措施是只读验证器。实现规则：

- 验证器与团队共享状态（读取黑板或消息池）。
- 验证器没有共享状态的写入句柄 —— 只能写入单独的验证通道。
- 验证器独立获取写入中引用的来源。标记不一致之处。
- 验证器自己的输出被路由到人类或单独的决策智能体，永远不会回流到池中。

没有这种分离，验证器的输出会成为池中的新条目，这意味着被投毒的池会投毒验证器，进而投毒其验证结果。

## 开始构建

`code/main.py` 使用标准库 Python 实现了两种拓扑，以及一个简单的投毒攻击和三种缓解措施。

- `MessagePool` — 线程安全的仅追加日志，支持完整读出。
- `Blackboard` — 基于主题键的发布/订阅，支持按智能体订阅。
- `ProvenanceEntry` — 每次写入记录（写入者、时间戳、提示词哈希、来源 URI）。
- `PoisoningScenario` — 运行一个三智能体研究任务，其中智能体 A 幻觉了一个小数点。打印最终报告。
- `Verifier` — 一个只读智能体，重新获取来源并标记不一致之处。在有验证器的情况下运行相同场景。

运行：

```
python3 code/main.py
```

预期输出：
- 运行 1（无验证器）：幻觉的 42% 传播到最终报告。
- 运行 2（有验证器）：验证器标记了不一致，消息池被标记为"已标记"，最终报告包含撤回声明。

## 实际应用

`outputs/skill-memory-auditor.md` 是一个审计任何多智能体系统共享记忆设计的技能，检查来源追溯、版本控制和验证器分离。在生产前对新的多智能体架构运行它。

## 投入生产

对于任何共享记忆设计：

- 在每次写入时记录来源：`(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`。
- 使日志仅追加。修正是引用被取代条目的新条目。
- 部署至少一个具有独立来源访问权限的只读验证器智能体。
- 将验证器输出路由到单独的通道，而不是回流到共享池中。
- 记录被取代写入的比例 —— 比例上升是幻觉模式的早期信号。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| 消息池 | "共享聊天历史" | 每个智能体读取的仅追加日志。完全透明，扩展性差。 |
| 黑板 | "共享工作空间" | 基于主题键的发布/订阅。智能体订阅相关主题。可扩展性更好。 |
| 来源追溯 | "谁写了什么" | 每次写入的元数据：写入者、时间戳、提示词、来源。 |
| 记忆投毒 | "幻觉传播" | 一个智能体的错误进入共享状态，下游智能体将其采纳为事实。 |
| 仅追加 | "没有就地更新" | 修正是取代旧条目的新条目。保留审计追踪。 |
| 不可写验证器 | "独立审计者" | 重新获取来源并标记不一致的只读智能体。 |
| 投影 | "有范围的视图" | 从全局状态计算的按智能体视图。LangGraph 归约器是典型用例。 |
| 知识源 | "专家智能体" | Hayes-Roth 1985 年对黑板参与者的术语。 |
