# 角色专业化——规划者、批评者、执行者、验证者

> 2026 年最常见的多智能体分解方式：一个智能体规划，一个执行，一个批评或验证。MetaGPT（arXiv:2308.00352）将其形式化为编码到角色提示中的标准操作流程（SOP）——产品经理、架构师、项目经理、工程师、QA 工程师——遵循 `Code = SOP(Team)` 的公式。ChatDev（arXiv:2307.07924）通过"对话链"将设计师、程序员、审查员、测试员串联起来，并采用"沟通式去幻觉"（智能体在缺失信息时主动请求补充）。验证者是核心角色：Cemri 等人（MAST，arXiv:2503.13657）表明，每个多智能体失败都可以追溯到缺失或失效的验证。PwC 报告称，在 CrewAI 中引入结构化验证循环后，准确率从 10% 提升到 70%，实现了 7 倍增益。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置要求：** 第 16 阶段 · 第 04 课（基础模型），第 16 阶段 · 第 05 课（监督者模式）
**所需时间：** 约 60 分钟

## 问题所在

通用的多智能体系统产出通用的输出。三个程序员在群聊中写出三种大同小异的平庸代码。你可以增加更多智能体、更多轮次，却仍然无法跨越质量门槛。

解决方案不是更多智能体——而是*不同的*智能体。分配不同的角色。给批评者规划者没有的工具。给验证者一套客观的测试用例。现在系统内部有了基于事实依据的分歧和纠正，而不仅仅是并行猜测。

## 概念说明

### 四个经典角色

**规划者（Planner）。** 阅读目标，产出步骤列表或规格说明。工具：知识检索、文档。输出：结构化计划。

**执行者（Executor）。** 每次读取一个计划步骤，产出工件。工具：实际工作工具（代码编译器、终端、API 客户端）。输出：工件。

**批评者（Critic）。** 对照规划者的意图审查执行者的输出。工具：对工件的只读访问、静态分析。输出：接受/拒绝及理由。

**验证者（Verifier）。** 读取工件并运行确定性检查。工具：测试运行器、类型检查器、模式验证器。输出：通过/失败及证据。

批评者是主观的、有判断力的、通常基于 LLM 的。验证者是客观的、确定性的、通常基于代码的。它们不是同一个角色。

### MetaGPT 的 SOP 模式

MetaGPT（arXiv:2308.00352）将软件工程 SOP 编码为角色提示：

- **产品经理** 编写 PRD。
- **架构师** 产出系统设计。
- **项目经理** 拆分任务。
- **工程师** 实现代码。
- **QA 工程师** 运行测试。

每个角色都有严格的输入/输出模式。角色提示定义了角色*是什么*以及*必须产出什么*。`Code = SOP(Team)` 的公式——确定性的 SOP 将一个 LLM 团队转变为可预测的流水线。

### ChatDev 的沟通式去幻觉

ChatDev 增加了一个关键动作：当执行者需要计划中未包含的具体细节时，它会在继续之前明确地向设计师询问。这防止了 LLM 编造细节的经典失败。

实现方式：角色提示中包含"当你需要未被提供的具体信息时，先向相关角色指名提问，然后再产出输出"。

### 为什么验证者最重要

Cemri 等人（MAST）追踪了 1642 次多智能体执行失败。21.3% 是验证缺口——系统提交了没人检查过的答案。其余 79% 往往可以追溯到"存在一项检查但静默失败或从未运行"。验证是承重角色。

PwC 报告（CrewAI 部署，2025 年）称，添加结构化验证循环后准确率从 10% 提升到 70%。一个角色带来了 7 倍增益。

### 批评者与验证者的区别

- 批评者是一个 LLM，审查工件的质量。主观。可能被看似合理的表述所迷惑。
- 验证者是一个确定性程序，对工件进行检查。客观。给出通过/失败及证据。

两者都要用。批评者能发现验证者无法表述的品味问题。验证者能抓住批评者看不到的 bug，因为这些 bug 只在运行时才会显现。

### 反模式

系统中的每个角色都是 LLM，每个角色的输出都是"看起来没问题"。典型的 MAST 失败模式。至少添加一个验证者，其通过/失败由代码而非 LLM 决定。

### 框架映射

- **CrewAI** — `Agent(role, goal, backstory)` 是教科书式的专业化接口。
- **LangGraph** — 节点可以拥有专业化的提示；边负责强制执行流水线。
- **AutoGen** — 专门的 ConversableAgent，以简洁命名在 GroupChat 中协作。
- **OpenAI Agents SDK** — 角色专业化 Agent 之间的交接工具。

## 开始构建

`code/main.py` 实现了一个 4 角色流水线，用于构建一个简单的 Python 函数：

- **规划者** 产出规格说明。
- **执行者** 生成代码字符串。
- **批评者**（LLM 模拟）标记明显的问题。
- **验证者** 在沙箱中（`exec`）对生成的代码运行测试用例。

演示运行两次：一次是执行者产出正确代码（批评者和验证者都通过），一次是执行者产出偏离规格的代码（批评者因为代码看似合理而遗漏了 bug，验证者因为测试失败而抓住了它）。

运行：

```
python3 code/main.py
```

## 实际应用

`outputs/skill-role-designer.md` 接受一个任务并产出角色名册（3-5 个角色）、每个角色的输入/输出模式以及验证者检查项。在将智能体接入框架之前使用。

## 投入生产

检查清单：

- **至少一个确定性验证者。** 绝不能全部是 LLM。
- **每个角色有明确的 I/O 模式。** 规划者返回规格说明，而非散文；执行者按该模式读取。
- **沟通式去幻觉。** 缺少信息时执行者必须询问规划者；绝不能自行编造。
- **批评者/验证者的执行顺序。** 先运行批评者（成本低，捕获设计问题），再运行验证者（速度慢，捕获 bug）。
- **循环预算。** 最多 2 轮批评者-执行者修订循环，之后升级给人类。

## 练习

1. 运行 `code/main.py`，观察验证者如何捕获批评者遗漏的 bug。添加一个静态分析检查（统计 `return` 出现次数）作为额外的验证者。它能捕获运行时测试遗漏的什么问题？
2. 添加第 5 个角色："需求分析师"，将用户需求转化为规划者可使用的规格说明。哪些沟通式去幻觉的请求应该向上流转给它？
3. 阅读 MetaGPT 第 3 节（"Agents"）。列出 MetaGPT 5 个角色各自的输入/输出模式。
4. 阅读 ChatDev 的对话链图（arXiv:2307.07924 图 3）。找出沟通式去幻觉在哪里打破了原本会无限循环的循环。
5. PwC 的 7 倍准确率增益来自验证循环。假设三个添加验证者不会有帮助的任务——在这些任务中，对正确性的确定性检查是不可能的或代价过高。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| 角色专业化 | "不同的智能体，不同的工作" | 针对规划者/执行者/批评者/验证者角色调优的独立系统提示。 |
| SOP 模式 | "编码化的标准操作流程" | MetaGPT 的框架：每个角色的严格 I/O 模式将团队转变为流水线。 |
| 沟通式去幻觉 | "先问再编" | ChatDev 模式：缺少细节时执行者向规划者提问，而非自行编造。 |
| 批评者 | "LLM 审查员" | 主观的、有判断力的审查者。捕获品味问题。可能被看似合理的表述所迷惑。 |
| 验证者 | "确定性检查" | 基于代码的通过/失败判定。测试运行器、类型检查器、模式验证器。不会被迷惑。 |
| 验证缺口 | "没人检查" | MAST 失败的 21.3%。答案在未经检查的情况下提交，而该检查本可以捕获 bug。 |
| 修订循环 | "批评者打回重做" | 批评者的拒绝触发执行者带反馈地重新运行。需要预算控制。 |
| 全 LLM 反模式 | "看起来没问题" | 每个角色都是 LLM，没有确定性检查。典型的 MAST 失败。 |
