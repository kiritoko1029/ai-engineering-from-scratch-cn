# 生产扩展——队列、检查点与持久性

> 将多智能体系统扩展到数千个并发运行需要**持久化执行**。LangGraph 的运行时在每个超级步骤后写入检查点，以 `thread_id` 为键（默认使用 Postgres）；工作者崩溃时释放租约，由另一个工作者恢复。智能体可以无限期休眠等待人类输入。**MegaAgent**（arXiv:2408.09955）为每个智能体运行一个生产者-消费者队列，具有三种状态（空闲/处理/响应）和两层协调（组内聊天 + 组间管理聊天）。**Fiber/异步**优于线程池方案，适用于 LLM 流式处理：线程 99% 的时间在等待 token 时空闲，而协程在 I/O 时协作让出。反面观点：Ashpreet Bedi 的"扩展智能体软件"主张在负载证明需要之前只用 **FastAPI + Postgres + 不多不少**——简单架构走得比预期更远。本课将构建一个持久化检查点日志、一个带状态转换的每智能体工作队列、一个异步与线程的对比演示，并落地务实的"从简单开始"规则。

**类型：** 学习 + 构建
**语言：** Python（标准库、`asyncio`、`sqlite3`）
**前置要求：** Phase 16 · 09（并行群体网络）、Phase 16 · 13（共享内存）
**所需时间：** 约 75 分钟

## 问题

一个原型多智能体系统在一台笔记本上运行三个智能体的内存事件循环。你将其推向生产环境：

- 智能体有时运行数小时（长时间研究、人在回路等待）。
- 工作进程崩溃。重启会丢失状态。
- 峰值负载是平均值的 10 倍；需要水平扩展。
- 用户按智能体运行次数付费；需要精确一次语义来计费。

内存事件循环无法实现以上任何一点。你需要一个持久化执行层。2026 年的标准选项有：

1. 带检查点的工作流引擎（Temporal、LangGraph 运行时）。
2. 带状态存储的消息队列（Postgres + SQS/RabbitMQ）。
3. Actor 模型框架（MegaAgent 的每智能体生产者-消费者）。
4. 手搓 FastAPI + Postgres（Bedi 的主张）。

本课将构建每种方案的迷你版本。

## 概念

### 持久化执行，模式

持久化执行引擎在每个"步骤"（LangGraph 术语中的超级步骤）之后持久化完整的程序状态。崩溃时：

```
worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects
```

使其工作的必要条件：

- **可序列化状态。** 所有智能体状态必须可持久化。带有活跃数据库连接的函数闭包无法存活。
- **确定性恢复。** 给定相同的状态和相同的输入，智能体产生相同的动作（或将 LLM 调用委托给外部确定性预言机）。
- **幂等副作用。** 外部调用（工具调用、支付）必须是幂等的或使用去重键。

LangGraph 在每个超级步骤后写入检查点；Temporal 在每个活动后写入；Restate 使用事件溯源日志。三者实现了相同的模式。

### LangGraph 的运行时

每个智能体有一个 `thread_id`；状态是类型化字典；每个超级步骤向检查点表写入一行。恢复时，运行时从最后一个检查点重放，而非从头开始。智能体可以 `interrupt()` 等待人类输入；运行时持久化状态并释放工作者。当输入到达时，任何工作者都可以恢复。

这是 2026 年 4 月的参考生产设计。

### MegaAgent 的每智能体队列

arXiv:2408.09955 描述了一个规模实验：一个集群中数千个并发智能体。架构：

```
agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)
```

两层协调使组内对话可以密集进行，而组间保持稀疏——这是在数千智能体中保持线性成本的模式。

### 异步与线程池

LLM 调用是 I/O 密集型的。等待下一个 token 的线程 99% 的时间处于空闲状态。每个线程占用约 1MB 内存；在 10,000 个并发调用时，仅栈空间就需要 10GB。

协程（Python `asyncio`、Go goroutine、Rust `tokio`）在 I/O 时协作让出。同样的 10,000 个调用可以轻松放入单个进程中。在 LLM 智能体规模下，异步不是优化——它是架构。

例外：CPU 密集型后处理（嵌入、分词器技巧）仍然需要线程或进程。将 I/O 层与 CPU 层分离。

### Bedi 的反面观点

"扩展智能体软件"（Ashpreet Bedi，2026）认为大多数团队在测量负载之前就过度工程化了。务实的默认方案：

- FastAPI + Postgres。
- 每次智能体运行是一行记录；状态通过乐观并发就地更新。
- 后台任务通过 `pg_notify` 或简单的 Celery 工作者实现。
- 应用代码中的重试策略。

对于可管理任务上约 100 个以下并发智能体运行的负载，这通常就是你所需要的全部。当你测量到它失败时再升级。

规则：当你遇到简单架构无法解决的具体问题时，才采用持久化执行框架。过早采用会在不产生回报的仪式上浪费时间。

### 精确一次语义

对于付费的智能体运行，你需要"精确一次有效"（至少一次投递 + 幂等消费者）。工程手段：

- **每次运行的去重键。** 将其包含在每个副作用调用中。
- **发件箱模式。** 副作用先写入表，然后由单独的进程执行。两个步骤都是幂等的。
- **补偿事务。** 当副作用成功但其跟踪写入失败时，安排补偿。

这些是数据库工程模式，而非 LLM 特有的。LLM 的额外成本仅在于 LLM 调用速度慢；其他一切都是标准分布式系统。

### 彩虹部署

Anthropic 的多智能体研究系统使用"彩虹部署"：多个版本的智能体运行时同时运行，这样长时间运行的智能体不必在每次代码部署时被终止。在一小部分流量上金丝雀测试新版本；当旧版本的智能体完成后退役。

这是长时间运行有状态系统的标准做法；2026 年的适应是智能体可以存活数小时，因此部署周期必须相应调整。

### 标准生产检查清单

- 持久化状态（检查点、快照或发件箱 + 可重放日志）。
- 幂等副作用。
- LLM 调用的异步 I/O 层。
- 至少一次投递加去重。
- 有状态工作负载的彩虹/金丝雀部署。
- 可观测性：每智能体追踪、超级步骤审计、重试计数器。

## 开始构建

`code/main.py` 实现了：

- `CheckpointStore` ——基于 SQLite 的检查点日志，以 thread-id 为键。每个超级步骤追加一行。
- `run_with_checkpoint(agent, thread_id)` ——模拟运行中崩溃；第二个工作者从最后一个检查点恢复。
- `AgentQueue` ——每智能体的空闲/处理/响应状态机，带有小型工作队列。
- `demo_async_vs_threads()` ——通过 asyncio 和线程分别运行 500 个并发模拟"LLM 调用"；报告墙钟时间和峰值内存（近似值）。

运行：

```
python3 code/main.py
```

预期输出：模拟崩溃后检查点恢复成功；异步版本在不到 1 秒内处理 500 个并发调用；线程版本耗时数秒，且每个并发单元的内存使用量高出数个数量级。

## 投入生产

标准生产加固：

- **从简单开始（Bedi 的规则）。** FastAPI + Postgres，直到你测量到它失败。
- **在优化之前先全面埋点。** 每次运行的延迟直方图、每步骤耗时、重试次数、故障分类。
- **副作用使用发件箱模式。** 尤其是支付和外部 API 调用。
- **彩虹部署。** 部署期间永远不要终止正在进行的智能体运行。
- **当你遇到具体问题时采用持久化执行引擎（Temporal / LangGraph / Restate）：** 长时间的人在回路等待、跨区域协调、复杂的重试/补偿策略。
- **I/O 层使用异步。** 线程仅用于 CPU 密集型后处理。

## 练习

1. 运行 `code/main.py`。确认检查点恢复正常工作；测量异步与线程的并发差异。
2. 实现一个**发件箱**表：每个工具调用先写入发件箱，然后由单独的 goroutine/任务执行。通过运行工具调用两次来验证幂等性。
3. 模拟**彩虹部署**：两个并发运行时版本；将一半新 thread_id 路由到每个版本；确认旧版本上正在进行的线程不会被中断。
4. 阅读 LangGraph 的运行时文档（链接见下文）。找出运行时的哪些功能在手搓 FastAPI + Postgres 版本中需要最长时间来复制。这是采用的理由，还是可以推迟？
5. 阅读 MegaAgent（arXiv:2408.09955）第 3 节。两层协调（组内 + 组间管理聊天）是显式的。草拟你如何将其映射到具有两个队列族的消息队列。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| 持久化执行 | "持久化程序状态" | 引擎在每个超级步骤后写入状态；崩溃恢复是确定性的。 |
| 超级步骤 | "事务边界" | 检查点之间的工作单元。LangGraph 术语。 |
| thread_id | "智能体运行标识符" | 绑定检查点和恢复逻辑的键。 |
| 幂等性 | "安全重试" | 重复执行副作用产生与单次执行相同的结果。 |
| 发件箱模式 | "解耦副作用" | 将意图写入表；单独的执行器执行并标记完成。 |
| 至少一次投递 | "可能重复" | 消息队列语义；去重键使消费者实现精确一次。 |
| 彩虹部署 | "多版本并行" | 在长时间运行工作负载期间多个运行时版本并存。 |
| 异步协程 | "协作让出" | 用户态并发；对于 I/O 密集型负载比线程更轻量。 |
| 检查点 | "状态快照" | 超级步骤边界处的序列化状态；恢复的关键。 |
