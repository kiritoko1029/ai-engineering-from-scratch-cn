# 监督者 / 编排器-工作者模式

> 一个主导智能体负责规划和委派；专家工作者在并行上下文中执行并汇报。这是 Anthropic 研究系统背后的模式（Claude Opus 4 作为主导，Sonnet 4 作为子智能体），在内部研究评估中比单智能体 Opus 4 高出 +90.2%。Anthropic 的工程博文报告称，BrowseComp 上 80% 的方差仅由 token 使用量解释——多智能体胜出主要是因为每个子智能体获得了一个全新的上下文窗口。本课从原语构建监督者模式，并涵盖 2026 年生产部署中的工程经验。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`）
**前置课程：** 第 16 阶段 · 04（原语模型）
**时间：** 约 75 分钟

## 问题

研究是单智能体系统失败的典型任务。你问"2023 到 2026 年间多智能体系统有什么变化？"单个智能体按顺序阅读五篇论文，用论文文本填满一半上下文，然后必须对所有论文一起进行推理。它读到第五篇时已经忘记了第一篇。它无法并行化。

监督者模式解决了这个问题：一个主导智能体规划搜索，将每个子问题委派给一个工作者，然后进行综合。每个工作者为一个狭窄的问题获得自己的 200k token 窗口。主导者从不看原始论文——只看工作者的摘要。

Anthropic 的生产研究系统在内部研究评估中比单个 Opus 4 高出 +90.2%。同一篇博文指出，BrowseComp 上 80% 的方差仅由*token 使用量*解释。每个子智能体获得全新上下文是主要机制。

## 概念

### 模式

```
                 ┌──────────────┐
                 │   Lead       │  plans, decomposes,
                 │  (Opus 4)    │  synthesizes
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ Worker1 │  │ Worker2 │  │ Worker3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         fresh       fresh        fresh
         context     context      context
```

主导者从不读取原始材料。工作者在主导者综合之前看不到彼此的工作。每条箭头都是一次带有狭窄工件的移交。

### 为什么它胜出

三个机制：

1. **每个子智能体获得全新上下文。** 探索"FIPA-ACL 传承"的工作者不携带主导者花在规划上的 40k token。它为一个问题获得 200k 窗口。
2. **通过提示词专业化。** 主导者的提示词是"分解和综合"，而非"研究"。每个工作者的提示词是狭窄的："找出 X 有什么变化"。专注的提示词产生专注的输出。
3. **并行化。** 工作者并发运行。挂钟时间大致是 `max(worker_times) + plan + synthesis`，而非 `sum(worker_times)`。

### 工程经验（Anthropic 2025）

Anthropic 的博文列出了几条至今仍适用于 2026 年的生产经验：

- **按查询复杂度调整投入。** 简单查询：一个智能体，3-10 次工具调用。复杂查询：10+ 个智能体。主导者必须估算这一点，而非调用者。
- **先广后窄。** 先将问题分解为广泛的子问题，如果答案需要深度，再为每个子问题生成更多工作者。
- **彩虹部署。** 智能体是长时间运行且有状态的。传统的蓝绿部署不适用。Anthropic 使用彩虹部署：新版本渐进式发布，同时旧版本排空。
- **Token 使用量占主导。** 多智能体的 token 消耗约为单智能体的 15 倍。只有当任务价值证明成本合理时才运行。

### LangGraph 的转变

LangGraph 最初发布了一个 `langgraph-supervisor` 库，带有高级 `create_supervisor` 辅助函数。2025 年，LangChain 将推荐改为通过直接工具调用来实现监督者模式，因为工具调用对*监督者看到什么*（上下文工程）有更多控制。该库仍然可用；文档现在推荐工具调用形式。

### 失败模式

- **主导者幻想计划。** 如果主导者生成的子问题没有真正分解问题，工作者会对错误目标进行精确研究。
- **工作者过度探索。** 没有明确的范围边界，工作者会偏离其分配的子问题并污染综合步骤。
- **综合冲突。** 两个工作者返回矛盾的事实。主导者要么重新提问（增加一轮），要么显式记录分歧。静默选择一方是最糟糕的失败：用户永远不知道发生了分歧。

### 何时不该使用监督者

- **顺序任务。** 如果步骤 2 确实需要步骤 1 的输出，并行化没有收益。使用流水线（CrewAI Sequential、LangGraph 线性图）。
- **简单查询。** 单智能体处理更快更便宜。在生成工作者之前使用主导者的"调整投入"检查。
- **严格确定性。** 监督者使用 LLM 选择的委派。当审计/重放比适应性更重要时，静态图更好。

## 动手构建

`code/main.py` 使用 `threading` 实现了一个包含三个并行工作者的监督者。主导者将查询分解为子问题，工作者在每个子问题上并发运行，主导者进行综合。没有真实的 LLM——工作者是脚本化的，模拟获取和摘要。

关键结构：

- `Lead.plan(query)` 将查询拆分为 3 个子问题。
- `Worker.run(sub_q)` 返回一个假摘要（在生产中可以是任何使用工具的智能体）。
- `Lead.run(query)` 在线程中启动工作者，等待它们完成，然后综合。

运行：

```
python3 code/main.py
```

输出显示计划、带开始/结束时间戳的并行工作者追踪，以及最终综合。你可以看到挂钟收益：三个 0.3 秒的工作者在约 0.35 秒内运行，而非 0.9 秒。

## 应用

`outputs/skill-supervisor-designer.md` 接收用户查询并产生监督者模式设计：主导系统提示词、工作者角色、子问题分解规则和综合模板。在构建新的研究型智能体系统之前使用它。

## 交付

部署监督者模式前的检查清单：

- **模型配对。** 主导者使用推理级模型（Opus 级别、`o3` 级别）。工作者使用更快、更便宜的模型（Sonnet、`o4-mini`）。
- **工作者超时。** 任何超过中位运行时间 2 倍的工作者会被终止；主导者要么用更窄的范围重新生成，要么在没有它的情况下继续。
- **每个工作者的 token 上限。** 硬限制（比如预期综合输入的 10 倍）防止失控的工作者耗尽预算。
- **可观察性。** 追踪主导者的计划、每个工作者的工具调用和综合。这是事后调试的基础。
- **彩虹发布。** 有状态的长时间运行智能体需要渐进式版本过渡，而非热替换。

## 练习

1. 运行 `code/main.py`，然后修改主导者使其生成 5 个工作者而非 3 个。观察挂钟效果。在这个演示中，工作者数量达到多少时，生成开销会超过并行收益？
2. 实现工作者超时：终止运行超过 0.5 秒的任何工作者，让主导者综合剩余结果。你需要什么可观察性来知道工作者被切断了？
3. 在主导者的综合中添加冲突检测步骤：如果两个工作者返回矛盾的答案，主导者记录分歧而非选择一方。你如何在不调用 LLM 的情况下检测矛盾？
4. 阅读 Anthropic 的研究系统工程博文。列出这个玩具演示要投入生产需要采用的三个实践。
5. 比较 LangGraph 的 `create_supervisor`（旧版）与新的工具调用推荐。哪个给你更好的控制来管理监督者看到什么？为什么 Anthropic 明确只将子答案而非原始工作者上下文传入综合？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| 监督者（Supervisor） | "主导智能体" | 一个编排器智能体，负责规划、委派和综合。不执行实际工作。 |
| 工作者（Worker） | "子智能体" | 由监督者调用的专注智能体，具有狭窄的范围和自己的上下文窗口。 |
| 编排器-工作者（Orchestrator-worker） | "监督者模式" | 同一件事，不同名称。2026 年的文献两者都使用。 |
| 全新上下文（Fresh context） | "干净窗口" | 工作者的上下文从其系统提示词和分配的问题开始，而非主导者的历史。 |
| 彩虹部署（Rainbow deployment） | "渐进式发布" | 长时间运行的有状态智能体需要版本化的排空和替换，而非蓝绿部署。 |
| Token 主导（Token dominance） | "上下文是变量" | 根据 Anthropic，研究评估 80% 的方差来自总 token 使用量，而非模型选择。 |
| 调整投入（Scale effort） | "匹配智能体数量与复杂度" | 主导者估算查询难度，相应地生成 1 个或 10+ 个工作者。 |
| 综合冲突（Synthesis conflict） | "工作者意见不一" | 两个工作者返回矛盾的事实；主导者必须浮现分歧，而非静默选择一方。 |
