# 并行 / 群体 / 网络化架构

> 与监督者模式的对比：没有中央决策者。代理读取共享事件总线，异步拾取工作，将结果写回。LangGraph 明确支持"群体架构"用于去中心化的动态环境。Matrix（arXiv:2511.21686）将控制流和数据流都表示为通过分布式队列传递的序列化消息，以消除编排者的瓶颈。取舍是明确的：用确定性和可追溯性换取可扩展性。群体架构适合有大量独立子任务的场景；不适合需要单一连贯计划的任务。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`，`queue`）
**前置要求：** 第 16 阶段 · 第 05 课（监督者模式），第 16 阶段 · 第 04 课（基础模型）
**所需时间：** 约 75 分钟

## 问题所在

监督者模式可以扩展到少量工作者。那几百个呢？监督者本身成为瓶颈：关于谁做什么的每个决策都经过一个代理。一个缓慢的计划步骤会阻塞整个系统。

群体架构颠覆了这种设计。不是由中央调度者分配工作，而是工作者从共享队列中拾取工作。"协调"被内化到事件总线的语义中。没有编排者；系统可以一直扩展到队列的极限。

## 概念说明

### 结构形态

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

没有编排者。每个工作者重复：拉取任务、处理、写入结果（可选择性地将后续任务入队）。

### 适用场景

- **大量独立任务。** 抓取、转换、分类。任务之间互不依赖。
- **时长不一的工作。** 如果某些任务需要 100ms 而另一些需要 10s，群体架构会自动平衡负载——快速工作者拉取下一个任务。监督者则需要预估时长。
- **吞吐量优先于确定性。** 你关心的是总完成时间，而非严格的顺序。

### 不适用场景

- **有序工作流。** 如果第 3 步需要第 2 步的输出，群体架构存在第 3 步在第 2 步完成前触发的风险。
- **需要全局计划的任务。** 复杂的研究问题需要规划者。一群研究员各自产出独立的事实，无法形成连贯的报告。
- **调试困难。** 没有中央日志，工作又是异步的，重现 bug 的代价很高。

### Matrix（arXiv:2511.21686）

Matrix 是 2025 年的论文，将群体架构推向了其自然结论：控制流和数据流都是分布式队列上的序列化消息。没有中央协调者。容错来自消息的持久性。可扩展性是消息代理的问题，而不是系统的问题。

贡献：一种编程模型，多智能体协调变成了"这个智能体订阅什么消息主题？"而非"监督者下一个选择哪个智能体？"。这使得系统看起来像一个发布/订阅事件网格。

### LangGraph 的群体架构

LangGraph 2025 文档明确将"群体架构"描述为多智能体模式之一：智能体是节点，但边形成带环的有向图，任何节点都可以从池中被激活。工作者按条件从可用工作中拾取，而非由监督者分配。

### 失败模式：饥饿与热点

如果所有工作者都拉取最快可用的任务，耗时长的任务永远不会被拾取，直到它们成为队列中仅剩的任务。典型的队列饥饿问题。

缓解措施：
- 带有显式老化机制的优先队列（随等待时间增加优先级）。
- 工作者专业化：部分工作者只接受"长耗时"任务。
- 背压：限制快速任务进入队列的数量。

### 与基于内容路由的关联

群体架构与基于内容路由（第 22 课）天然契合。不是使用通用队列，而是为每种消息类型维护一个队列。专业工作者只订阅自己负责的类型。这是消息总线架构扩展到数千个智能体的基础。

## 开始构建

`code/main.py` 实现了一个包含 4 个工作线程的群体，从共享的 `queue.Queue` 中拉取任务。任务有不同的时长（有些快，有些慢）。演示对比了：

- **顺序基线：** 一个工作者串行处理所有任务。
- **固定分配：** 每个任务预先分配给特定工作者（监督者模式）。
- **群体模式：** 工作者从共享队列中拉取。

群体模式自动平衡负载；固定分配模式下，当分配的任务较慢时，快速工作者会闲置。

运行：

```
python3 code/main.py
```

输出展示了每个工作者的任务计数（群体模式分配不均匀但最优）和实际耗时。

## 实际应用

`outputs/skill-swarm-fit.md` 评估任务应使用群体架构还是监督者模式。输入：任务独立性、时长方差、排序需求、可调试性需求。

## 投入生产

检查清单：

- **带老化机制的优先队列。** 防止长任务饥饿。
- **工作者幂等性。** 如果工作者在运行中途崩溃，任务可能被重复拉取。工作者必须是幂等的。
- **持久化队列。** 生产环境使用 Kafka、Redis Streams 或数据库支持的队列。`queue.Queue` 仅在内存中。
- **每个任务的可观测性。** 每个任务都有一个追踪 ID；每个工作者用它记录开始/结束。
- **背压。** 如果队列增长速度超过工作者的消费速度，需要减慢生产者。

## 练习

1. 运行 `code/main.py`。在时长不一的工作负载下，群体模式比顺序模式快多少？比固定分配快多少？
2. 添加优先队列变体（使用 `queue.PriorityQueue`）。按任务的"重要性"字段分配优先级。观察在持续负载下低优先级任务是否会出现饥饿。
3. 实现热点检测器：当某个工作者处理的任务数是最慢工作者的 3 倍以上时记录日志。这说明任务时长分布有什么特征？
4. 阅读 Matrix 论文（arXiv:2511.21686）的摘要和第 3 节。找出 Matrix 接受的一个具体权衡（可扩展性增益）和放弃的一个方面（可追溯性、确定性）。
5. 将群体演示改为使用 `(task_type, payload)` 元组的 `queue.Queue`，工作者只订阅特定类型。当任务具有异构性时，什么路由规则是合理的？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| 群体架构 | "去中心化代理" | 工作者从共享队列拉取工作；没有中央编排者。 |
| 事件总线 | "代理订阅主题" | 按类型或内容将任务路由给工作者的消息代理。 |
| 饥饿 | "任务永远不运行" | 低优先级任务因高优先级工作持续到达而永远不被拾取。 |
| 热点 | "一个工作者不堪重负" | 负载不均衡，某个工作者获得大部分任务。 |
| 背压 | "减慢生产者" | 当队列满时通知上游停止生产的机制。 |
| 幂等工作者 | "可以安全重跑" | 任务处理两次产生相同结果。因为工作者可能在运行中途崩溃，所以这是必需的。 |
| 持久化队列 | "崩溃后不丢失" | 由磁盘或复制存储支持的队列；工作者崩溃时任务不会丢失。 |
| Matrix 框架 | "完全消息传递式群体" | 数据流和控制流都是分布式队列上的序列化消息。 |
