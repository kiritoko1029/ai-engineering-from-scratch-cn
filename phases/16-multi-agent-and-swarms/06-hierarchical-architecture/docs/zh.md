# 层级架构及其失败模式

> 层级架构是嵌套式的监督者模式。管理者代理之上还有子管理者，子管理者之上才是工作者。CrewAI 的 `Process.hierarchical` 是教科书式的实现：一个 `manager_llm` 动态分配任务并验证输出。LangGraph 的等价实现是 `create_supervisor(create_supervisor(...))`。当任务本身就是一个真实的组织架构图时，这是最自然的模式。但它也是最容易陷入管理循环的模式——管理者代理分配不当、误解子任务输出，或无法达成共识。顺序执行往往比它更可靠。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置要求：** 第 16 阶段 · 第 05 课（监督者模式）
**所需时间：** 约 60 分钟

## 问题所在

一旦监督者模式跑通了，下一步自然是"如果工作者本身也是监督者呢？"团队有子团队；公司有部门套部门。层级架构正是这种结构的映射。

问题在于：LLM 管理者和人类管理者不一样。人类管理者对其下属的能力有稳定的先验认知。而 LLM 管理者每一轮都要根据上下文中的内容重新推理组织结构。上下文稍有偏移，整棵树就会错误地分配工作。

## 概念说明

### 结构形态

```
                 Manager
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       Sub-Mgr A         Sub-Mgr B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每个内部节点负责规划、分配和综合。只有叶子节点执行实际工作。

### 适用场景

- **清晰的组织映射。** 如果真实任务就是跨部门的（"法务审查文档，财务审查文档，工程审查文档，然后向管理层汇报总结"），层级结构就是显而易见的选择。
- **局部摘要。** 每个子管理者在上级管理者查看之前，先综合其团队的输出。上级管理者看到的是三个子管理者的摘要，而不是十五个工作者的原始输出。

### 失败模式

2026 年的事后复盘中反复出现三种失败模式：

1. **任务分配错误。** 管理者阅读目标后，幻觉出一种分解方式，将任务分配给了错误的子管理者。由于子管理者会忠实地执行分配给它的任务，错误直到顶层综合时才会暴露——此时距离本应有人发现问题的地方已经隔了一层。
2. **输出误解。** 子管理者返回"无法验证声明 X"。上级管理者将其摘要为"声明 X 未得到确认"。含义在每一层都在漂移。
3. **共识循环。** 两个子管理者意见不一致；上级管理者要求他们协调；他们重新向下分配；工作者重新运行；子管理者返回略有不同的答案；如此循环。CrewAI 的 `Process.hierarchical` 通过步数限制来防止这种情况，但限制本身现在成了一个超参数。

### 关键决策问题

顺序执行（线性流水线）与层级架构的选择：你的任务是否真的有独立的子团队，还是只是一个伪装成树状结构的线性流程？如果是后者，用顺序执行。如果是前者，用层级架构，但需要设定明确的协调规则。

### CrewAI 的实现

`Process.hierarchical` 在专业团队之上连接一个管理者 LLM。该管理者：

- 接收顶层任务，
- 将子任务分配给各团队，
- 评估团队输出，
- 决定是接受、重新分配还是迭代。

文档：https://docs.crewai.com/en/introduction（在 Core Concepts 下查找 "Hierarchical Process"）。

### LangGraph 的实现

LangGraph 使用嵌套的 `create_supervisor` 调用。内部监督者拥有自己的图；外部监督者将内部图视为一个不透明节点。这在调试方面比 CrewAI 更清晰（你可以分别单步执行每个图），但更难表达树的动态重构。

参考：https://reference.langchain.com/python/langgraph-supervisor。

## 开始构建

`code/main.py` 运行一个 3 层层级结构：

- 顶层管理者：将任务拆分为"工程"和"法务"两个分支，
- 工程子管理者：拆分为"前端"和"后端"工作者，
- 法务子管理者：一个工作者。

演示对比了正常路径（所有人达成一致）与**扰动路径**——顶层管理者的分解错误地将"法务"标记为"财务"，并观察错误如何级联传播：子管理者忠实地执行财务工作，顶层综合者汇报财务发现，而原始的法务问题却无人应答。

运行：

```
python3 code/main.py
```

输出展示了两条路径，清晰地并排对比"问题是什么"与"实际交付了什么"。

## 实际应用

`outputs/skill-hierarchy-fitness.md` 评估给定任务应使用层级架构、顺序执行还是扁平监督者。输入：任务描述、组织结构、协调预算。输出：模式推荐及需防范的具体失败模式。

## 投入生产

如果要部署层级架构：

- **限制树深度为 2 层。** 三层以上会将大部分错误隐藏在可观测性之外。
- **明确协调预算。** 设置顶层管理者必须做出决定前的最大轮数，通常为 2 轮。
- **每次综合都标注来源。** 每个节点的摘要必须引用是哪些叶子节点的输出产生了该摘要。
- **检测分解漂移。** 记录管理者每一步的分解结果；与用户查询进行对比。如果分解不再覆盖查询，触发告警。

## 练习

1. 运行 `code/main.py`，对比正常路径与扰动路径。经过多少层管理者传递后，顶层输出才与用户问题完全偏离？
2. 添加第三层（顶层 → 子层 → 子子层 → 工作者）。随着深度增加，测量扰动路径自我纠正与完全偏离的频率各是多少。
3. 在每个子管理者处实现一个"金丝雀"工作者，始终被问及原始用户问题（不做修改）。使用金丝雀的答案来检测分解漂移。当金丝雀的答案与综合答案不一致时，管理者应如何应对？
4. 阅读 CrewAI 的 `Process.hierarchical` 文档。找出 CrewAI 应用的一个具体防护措施（步数限制、manager_llm 约束等），并描述它针对的是哪种失败模式。
5. 比较嵌套 LangGraph 监督者与 CrewAI 层级架构。哪种方式使协调循环更容易被检测到？

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| 层级架构 | "组织架构模式" | 监督者之上的监督者；只有叶子节点执行实际工作。 |
| 管理者 LLM | "老板" | 在内部节点进行分解、分配和验证的 LLM。 |
| 分解漂移 | "老板跑偏了" | 顶层管理者的拆分不再覆盖原始问题。 |
| 协调循环 | "没完没了的会议" | 子管理者意见不一致；顶层重新分配；工作者重新运行；循环直到预算耗尽。 |
| 深度上限 2 | "不要超过 2 层" | 经验性防护：3 层以上会丧失可观测性。 |
| 金丝雀问题 | "每一层的基准真相" | 一个始终被问及原始查询（不做修改）的工作者，用于检测漂移。 |
| 来源链 | "谁说了什么" | 从每次综合追溯到产生它的叶子节点输出。 |
