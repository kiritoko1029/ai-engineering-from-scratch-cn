# 交接与例程 — 无状态编排

> OpenAI 的 Swarm（2024 年 10 月）将多智能体编排提炼为两个原语：**例程**（指令 + 工具作为系统提示词）和**交接**（一个返回另一个 Agent 的工具）。没有状态机，没有分支 DSL —— LLM 通过调用正确的交接工具来路由。OpenAI Agents SDK（2025 年 3 月）是其生产级后续版本。Swarm 本身仍是最简洁的概念参考 —— 其全部源代码仅几百行。该模式之所以广为传播，是因为其 API 表面大致为"agent = prompt + tools；handoff = 返回 agent 的函数"。局限性：无状态，因此记忆管理是调用者的问题。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置要求：** 第 16 阶段 · 04（原始模型）
**所需时间：** 约 60 分钟

## 问题

每个多智能体框架都要求你学习它的 DSL：LangGraph 的节点和边、CrewAI 的团队和任务、AutoGen 的 GroupChat 和管理器。DSL 是真正的抽象，但它们让事情变得比实际需要的更重。

Swarm 走的是相反的方向：利用模型已有的工具调用能力。交接变成工具调用。编排器就是当前持有对话的智能体。状态机隐含在智能体的系统提示词中。

## 概念

### 两个原语

**例程。** 一个系统提示词，定义智能体的角色和可用工具。可以将其视为一组有范围的指令："你是一个分诊智能体；如果用户询问退款，请移交给退款智能体。"

**交接。** 智能体可以调用的一个工具，返回一个新的 Agent 对象。Swarm 运行时检测到 Agent 返回值后，会在下一轮切换活跃智能体。

这就是全部抽象。

```python
def transfer_to_refunds():
    return refund_agent  # Swarm sees Agent return → switch active agent

triage_agent = Agent(
    name="triage",
    instructions="Route the user to the right specialist.",
    functions=[transfer_to_refunds, transfer_to_sales, transfer_to_support],
)
```

分诊智能体的系统提示词使其根据用户消息选择正确的交接。LLM 的工具调用完成路由。

### 为什么它广为传播

- **小型 API。** 只需学习两个概念。
- **利用模型已有的能力。** 工具调用在各供应商中已经是生产级的。
- **没有状态机负担。** 你不需要描述图；智能体的提示词描述了它们向谁交接。

### 无状态的权衡

Swarm 在运行之间是显式无状态的。框架在一次运行期间维护消息历史，但不会持久化任何内容。记忆、连续性、长时间运行的任务 —— 全部是调用者的问题。

在生产环境（OpenAI Agents SDK，2025 年 3 月）中，这是主要改变之一：SDK 在保留交接原语的同时，添加了内置的会话管理、防护栏和追踪功能。

### Swarm/交接适用场景

- **分诊模式。** 前线智能体将用户路由到专家。
- **基于技能的交接。** "如果任务需要编码，调用编码器；如果需要研究，调用研究员。"
- **简短、有边界的对话。** 客户支持、FAQ 转工单、简单的工作流。

### Swarm 的局限

- **具有共享记忆的长会话。** 交接会将对话状态重置为新智能体的提示词加上历史记录。没有调用者管理的内存，就没有跨智能体的持久状态。
- **并行执行。** 交接是逐个进行的 —— 活跃智能体会切换。并行需要调用者编排多个 Swarm 运行。
- **审计和重放。** 无状态运行难以精确重放；LLM 的交接选择不是确定性的。

### OpenAI Agents SDK（2025 年 3 月）

生产级后续版本新增：

- **会话状态。** 跨运行的持久线程。
- **防护栏。** 输入/输出验证钩子。
- **追踪。** 每个工具调用和交接都被记录。
- **交接过滤器。** 控制交接时传递的上下文。

交接原语得以保留；生产级的便利性围绕它逐步增强。

### Swarm 与 GroupChat 的对比

两者都使用 LLM 驱动的路由，但它们在**谁选择下一个**这一点上有所不同：

- GroupChat：一个选择器（函数或 LLM）从外部选择下一个发言者。
- Swarm：当前智能体通过调用交接工具来选择其继任者。

Swarm 是"智能体决定下一步"；GroupChat 是"管理者决定下一步"。Swarm 的决策位于活跃智能体的工具调用中；GroupChat 的决策位于 `GroupChatManager` 中。

## 开始构建

`code/main.py` 从零实现了 Swarm：一个 Agent 数据类、一个交接机制（工具返回 Agent），以及一个检测智能体切换的运行循环。

演示：一个分诊智能体路由到退款、销售或支持专家。每个专家有自己的工具。运行循环打印每次交接。

运行：

```
python3 code/main.py
```

## 实际应用

`outputs/skill-handoff-designer.md` 为给定任务设计交接拓扑：存在哪些智能体，它们可以调用哪些交接，传递什么上下文。

## 投入生产

检查清单：

- **交接日志。** 每次交接写入一个追踪事件，包含源智能体、目标智能体、上下文快照。
- **上下文传递规则。** 决定交接时传递什么：完整历史记录（成本高）、最近 N 条消息，或摘要。
- **交接防护。** 向具有不同工具权限的专家进行交接时必须经过认证 —— 否则提示词注入可以强制执行非预期的交接。
- **循环检测。** 两个智能体反复交接是常见的失败模式；使用简单的最近 K 次环形检查来检测。
- **兜底智能体。** 如果交接目标不存在，回退到一个安全的默认值。

## 练习

1. 运行 `code/main.py`，分诊到退款智能体。确认第二轮的活跃智能体是退款智能体。
2. 添加循环检测规则：如果相同的两个智能体连续交接 3 次，强制退出。设计兜底方案。
3. 阅读 OpenAI Agents SDK 文档中关于交接过滤器的内容。实现一个"交接时摘要"版本：传出的智能体在传入智能体接管之前将上下文压缩为要点摘要。
4. 比较 Swarm 交接与 GroupChatManager 选择器。哪种模式使提示词注入更严重，为什么？
5. 阅读 Swarm 手册（https://developers.openai.com/cookbook/examples/orchestrating_agents）。找出 Swarm 做出的一个明确设计决策，该决策在 OpenAI Agents SDK 中被更改或保留。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|---------|---------|
| 例程 | "智能体提示词" | 系统提示词 + 工具列表。定义角色和可用交接。 |
| 交接 | "转移到另一个智能体" | 活跃智能体可以调用的一个工具，返回新的 Agent。运行时切换活跃智能体。 |
| 无状态 | "运行之间没有记忆" | Swarm 不持久化任何内容；记忆是调用者的责任。 |
| 活跃智能体 | "现在谁在说话" | 当前持有对话的智能体。交接会改变这一点。 |
| 上下文传递 | "交接时传递什么" | 传入智能体可见历史记录的策略：完整、最近 N 条或摘要。 |
| 交接循环 | "智能体乒乓" | 两个智能体不断互相交接的失败模式。 |
| OpenAI Agents SDK | "生产级 Swarm" | 2025 年 3 月的后续版本；在交接原语之上增加了会话、防护栏和追踪。 |
| 交接过滤器 | "传递时的门控" | SDK 功能，在交接边界处检查和修改上下文。 |
