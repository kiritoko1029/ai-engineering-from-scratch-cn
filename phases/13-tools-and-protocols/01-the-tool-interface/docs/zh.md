# 工具接口 -- 为什么智能体需要结构化 I/O

> 语言模型产出 token，程序执行动作。两者之间的桥梁就是工具接口：一份契约，让模型能够请求某个动作，由宿主程序来执行。2026 年的所有主流技术栈 -- OpenAI、Anthropic 和 Gemini 上的函数调用；MCP 的 `tools/call`；A2A 的任务部件 -- 本质上都是同一个四步循环的不同编码形式。本课将为这个循环命名，并展示运行它所需的最小机制。

**类型：** 学习
**语言：** Python（标准库，无需 LLM）
**前置要求：** 第 11 阶段（LLM 补全 API）
**所需时间：** 约45分钟

## 学习目标

- 解释为什么只能生成文本的 LLM 无法自行对现实世界采取行动。
- 画出四步工具调用循环（描述 -> 决策 -> 执行 -> 观察），并说明每一步由谁负责。
- 将工具描述编写为三个部分：名称、JSON Schema 输入和确定性执行函数。
- 区分纯工具和副作用工具，并说明这种划分对安全性的意义。

## 问题所在

LLM 输出的是下一个 token 的概率分布，这就是它的全部输出能力。如果你问聊天模型"班加罗尔现在的天气怎么样"，它可以写出一句看似合理的话，但无法实际调用天气 API。这句话可能碰巧正确，也可能已经过时三天。

弥合这个差距就是工具接口存在的意义。宿主程序 -- 你的智能体运行时、Claude Desktop、ChatGPT、Cursor 或自定义脚本 -- 向模型公布一组可调用的工具。当模型判断需要采取行动时，会输出一个结构化载荷，指明工具名称和参数。宿主程序解析该载荷，真正执行工具，然后将结果反馈给模型。循环持续进行，直到模型判断不再需要调用为止。

这份契约的第一个版本于 2023 年 6 月随 OpenAI 的 `functions` 参数一起发布。Anthropic 在 Claude 2.1 中紧随其后推出了 `tool_use` 块。几个月后 Gemini 添加了 `functionDeclarations`。如今每个供应商都暴露相同的形式：输入是一个带 JSON Schema 类型定义的工具列表，输出是一个 JSON 载荷的工具调用。模型上下文协议（Model Context Protocol，2024 年 11 月）将这份契约泛化，使得一个工具注册表可以为所有模型服务。A2A（2026 年 4 月，v1.0）则在智能体间委派场景上叠加了同样的原语。

四步循环是所有这些方案背后不变的底层结构。第 13 阶段的其他内容都是对它的进一步阐述。

## 概念说明

### 第一步：描述

宿主程序通过三个字段来声明每个工具。

- **名称。** 稳定的、机器可读的标识符。例如 `get_weather`，而不是 "weather thing"。
- **描述。** 一段自然语言的简要说明。"当用户询问特定城市的当前天气状况时使用。不要用于历史数据查询。"
- **输入模式。** 一个 JSON Schema 对象（draft 2020-12），描述工具的参数。

模型接收到这个列表。现代供应商会使用特定模板将这些声明序列化到系统提示中，因此作为调用者你只需要处理结构化的形式。

### 第二步：决策

根据用户的消息和可用工具，模型会选择以下三种行为之一。

1. **直接回答**，以文本形式回复，不调用工具。
2. **调用一个或多个工具。** 输出结构化的调用对象。在 `parallel_tool_calls: true`（OpenAI 和 Gemini 默认开启，Anthropic 需要显式启用）下，模型可以在一轮中输出多个调用。
3. **拒绝。** 严格模式的结构化输出可以生成一个带类型的 `refusal` 块，而不是调用。

工具调用载荷包含三个固定字段：调用 `id`、工具 `name` 和 JSON `arguments` 对象。id 的存在是为了让宿主程序能够将后续结果与特定调用关联起来，这在并行调用乱序返回时尤为重要。

### 第三步：执行

宿主程序接收调用，根据声明的模式验证参数，然后运行执行器。参数无效意味着模型产生了幻觉字段或使用了错误类型 -- 这在弱模型上是一种非常常见的失败模式。生产环境中的宿主程序通常采取三种策略之一：快速失败并向模型报告错误、使用约束解析器修复 JSON、或将验证错误包含在提示中重试模型。

执行器本身是普通代码。Python、TypeScript、shell 命令、数据库查询都可以。它产生一个结果，通常是字符串，但可以是任何 JSON 值或结构化内容块（文本、图像或 MCP 中的资源引用）。结果必须是可序列化的。

### 第四步：观察

宿主程序将工具结果附加到对话中（作为 `tool` 角色的消息，并带有匹配的 `id`），然后重新调用模型。模型现在可以在上下文中看到工具的输出，从而生成最终回答或请求更多调用。这个过程持续进行，直到模型停止输出调用，或者宿主程序达到迭代次数的安全上限。

### 信任划分

工具在安全性方面有两种重要分类。

- **纯工具。** 只读、确定性、无副作用。例如 `get_weather`、`search_docs`、`get_current_time`。可以投机性地调用。
- **重大影响工具。** 会改变状态、花费资金、触碰用户数据。例如 `send_email`、`delete_file`、`execute_trade`。必须加以管控。

Meta 在 2026 年为智能体安全提出的"二元法则"指出：单轮对话最多只能组合以下三项中的两项：不可信输入、敏感数据、重大影响操作。工具接口正是你执行这条规则的地方 -- 通过拒绝调用、要求用户确认或升级权限范围。完整的安全章节见第 13 阶段第 15 课，智能体级别的权限策略见第 14 阶段第 09 课。

### 循环在哪里运行

| 场景 | 谁负责描述 | 谁负责决策 | 谁负责执行 |
|------|-----------|-----------|-----------|
| 单轮函数调用（OpenAI/Anthropic/Gemini） | 应用开发者 | LLM | 应用开发者 |
| MCP | MCP 服务器 | LLM（通过 MCP 客户端） | MCP 服务器 |
| A2A | Agent Card 发布者 | 调用方智能体 | 被调用方智能体 |
| Web 浏览器（函数调用智能体） | 浏览器扩展 / WebMCP | LLM | 浏览器运行时 |

无论在哪里，都是同样的四步。列名会变，结构不变。

### 为什么不直接让模型输出 JSON？

"要求模型以 JSON 格式回复"是函数调用出现之前的模式。在前沿模型上，它的失败率约为 5% 到 15%，在小模型上更高。失败模式包括缺少花括号、多余逗号、幻觉字段和类型错误。之后你需要 JSON 修复、重试或约束解码器。

原生函数调用在三个方面更优。首先，供应商端到端地按照精确的调用形式训练模型，因此在严格模式下有效 JSON 的比率提升到 98% 到 99%。其次，调用载荷位于独立的协议槽中，而非自由文本内部 -- 所以工具调用永远不会泄露到用户可见的回复中。第三，供应商通过约束解码来强制遵守模式（OpenAI 的严格模式、Anthropic 的 `tool_use`、Gemini 的 `responseSchema`）。输出保证通过验证。

### 断路器

当模型停止输出调用或宿主程序达到最大轮次限制时，循环终止。生产环境中的宿主程序通常将此设置为 5 到 20 轮。超过这个范围，你几乎可以确定模型陷入了无法退出的循环。Claude Code 默认为 20 轮；OpenAI Assistants 为 10 轮；Cursor 的智能体模式为 25 轮。

反面案例 -- 无界循环 -- 每隔六个月就会以"智能体一晚花掉 400 美元 API 调用费用"的复盘文章形式出现。不要在没有上限的情况下发布。

## 开始构建

`code/main.py` 在没有 LLM 的情况下运行四步循环。一个模拟的"决策器"函数通过模式匹配用户消息来模拟模型；执行器、模式验证器和观察步骤的脚手架是真实的。运行它可以看到完整的请求/响应编排，以及可打印的中间状态，然后在后续课程中用真实的供应商替换模拟决策器。

需要关注的要点：

- 工具注册表为每个工具保存三个字段：名称、描述、模式和一个执行器引用。
- 验证器是一个最小的 JSON Schema 子集（类型、required、enum、min/max），仅使用标准库编写。第 13 阶段第 04 课会提供更完整的版本。
- 循环将迭代次数限制在五次。生产环境的智能体恰恰需要这种断路器机制。

## 发布成果

本课生成 `outputs/skill-tool-interface-reviewer.md`。给定一个工具定义草案（名称 + 描述 + 模式 + 执行器概要），该技能会审计其循环适配性：名称是否机器稳定、描述是否是完整的使用说明、模式是否正确使用 JSON Schema 2020-12、以及纯工具与重大影响工具的分类是否明确。

2. 故意破坏模式验证器。传入一个 `arguments` 对象缺少必需字段的调用，确认宿主程序在执行前拒绝它。然后再传入一个包含多余未知字段的调用。思考：宿主程序应该拒绝还是忽略？请用安全性论证来证明你的选择。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 工具（Tool） | "模型可以调用的东西" | 名称 + JSON Schema 类型化输入 + 执行器函数的三元组 |
| 函数调用（Function calling） | "原生工具使用" | 供应商级别的 API 支持，用于输出结构化工具调用而非散文 |
| 工具调用（Tool call） | "模型的行动请求" | 模型输出的包含 `id`、`name`、`arguments` 的 JSON 载荷 |
| 工具结果（Tool result） | "工具返回的内容" | 执行器的输出，包装在带匹配 id 的 `tool` 角色消息中 |
| 并行工具调用（Parallel tool calls） | "一次调用多个" | 一轮模型输出中的多个调用对象，彼此独立且可按 id 排序 |
| 严格模式（Strict mode） | "保证 JSON" | 约束解码，强制模型输出符合声明的模式 |
| 纯工具（Pure tool） | "只读工具" | 无副作用；可安全重跑 |
| 重大影响工具（Consequential tool） | "行动工具" | 改变外部状态；需要门控、审计或用户确认 |
| 四步循环（Four-step loop） | "工具调用周期" | 描述 -> 决策 -> 执行 -> 观察 |
| 宿主（Host） | "智能体运行时" | 持有工具注册表、调用模型并运行执行器的程序 |
