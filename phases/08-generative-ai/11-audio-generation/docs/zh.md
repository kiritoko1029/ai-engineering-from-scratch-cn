# 音频生成

> 音频是一种频率范围为 16-48 kHz 的一维信号。一段五秒的音频片段包含 80-240k 个采样点。没有任何 Transformer 模型会直接处理该序列数据。截至 2026 年，所有商用音频模型的解决方案都是一样的：首先由神经编解码器（如 Encodec、SoundStream、DAC）将音频压缩为频率为 50-75 Hz 的离散令牌，随后再由 Transformer 或扩散模型生成这些令牌。

**类型：** 构建
**语言：** Python
**先修课程：** 第 6 阶段 · 02（音频特征）、第 6 阶段 · 04（语音识别）、第 8 阶段 · 06（DDPM）
**耗时：** 约 45 分钟

## 问题所在

三种音频生成任务：

1. **文本转语音。** 根据输入的文本生成语音。纯净的语音属于窄带信号，具有清晰的语音结构——这种场景非常适合通过基于令牌的Transformer模型来处理。代表性产品包括Microsoft的VALL-E、NaturalSpeech 3、ElevenLabs以及OpenAI的TTS。

2. **音乐生成。** 根据提示词（文本、旋律、和弦进行、音乐风格等）生成音乐。其输出范围更为广泛。代表性产品有Meta的MusicGen、Stable Audio 2.5、Suno v4、Udio以及Riffusion。

3. **音频效果/音效设计。** 根据提示词生成环境音或拟声效果。代表性产品包括AudioGen、AudioLDM 2以及Stable Audio Open。

这三种任务均基于相同的底层架构运行：神经音频编解码器 + 令牌自回归模型或扩散模型生成器。

## 概念概述

![音频生成：编解码器令牌 + 变换器或扩散模型](../assets/audio-generation.svg)

### 神经网络音频编解码器

Encodec（Meta，2022年）、SoundStream（Google，2021年）、Descript Audio Codec（DAC，2023年）。卷积编码器将波形压缩为每个时间步的向量；残差向量量化（RVQ）则将这些向量转换为一系列K个码本索引。解码器执行相反的操作。使用8个RVQ码本，在75赫兹采样率下以2千比特/秒的速率处理24千赫兹音频时，数据传输速率为600个标记/秒。

```
waveform (16000 samples/sec)
    └─ encoder conv ─┐
                     ├─ RVQ layer 1 → indices at 75 Hz
                     ├─ RVQ layer 2 → indices at 75 Hz
                     ├─ ...
                     └─ RVQ layer 8
```

### 两种上层生成范式

**令牌自回归模型。** 将RVQ令牌展平为序列，随后运行仅解码器的Transformer模型。MusicGen采用“延迟并行”策略，以流为单位生成代码本数据流，并为每个流设置偏移量。VALL-E则根据文本提示及3秒长的语音样本来生成语音令牌。

**潜在扩散模型。** 可将编解码器令牌打包为连续型潜在变量，或通过分类扩散方式对其进行建模。Stable Audio 2.5利用连续音频潜在变量的流匹配技术。AudioLDM 2则采用文本到梅尔频谱再到音频的扩散机制。

2024-2026年的发展趋势是：在音乐生成领域，流匹配技术因推理速度更快、生成的样本质量更优而逐渐占据优势；而在语音生成领域，令牌自回归模型仍占据主导地位，因其具有天然的因果结构且能实现高效的流式处理。

## 构建它

`code/main.py` 模拟了核心思想：在由两种不同“风格”生成的合成“音频令牌”序列上训练一个小型下一个令牌变换器（风格 A 采用低频与高频令牌交替，风格 B 则为单调递增的波形）。该模型会根据风格和样本进行条件化处理。

### 步骤 1：合成音频令牌

```python
def make_tokens(style, length, vocab_size, rng):
    if style == 0:  # "speech-like": alternating
        return [i % vocab_size for i in range(length)]
    # "music-like": ramp
    return [(i * 3) % vocab_size for i in range(length)]
```

### 步骤 2：训练一个小型令牌预测器

一种基于风格条件化的二元词预测模型。其核心流程为：编解码器令牌 → 交叉熵训练 → 自回归采样。

### 步骤 3：条件性采样

给定风格标记和起始标记，从预测的分布中采样下一个标记。如此重复生成20到40个标记。

## 常见陷阱

- **编解码器质量决定了输出质量的上限。** 如果编解码器无法忠实还原声音，再高的生成器质量也无济于事。目前最佳的方案是使用 DAC。
- **RVQ 错误累积问题。** 每一层 RVQ 都会对前一层的残差进行建模，第一层产生的错误会逐层传递。在更高层级采用温度值为 0 的采样方式有助于缓解这一问题。
- **音乐结构的影响。** 在 75 Hz 的采样率下，30 秒的音乐对应超过 2 万个 token，这对 Transformer 模型来说难度很大。MusicGen 采用滑动窗口与提示词续写相结合的方式；而 Stable Audio 则使用更短的音频片段并配合渐变过渡。
- **边界处的伪影问题。** 在生成的音频片段之间进行渐变过渡时，需要谨慎处理重叠叠加部分。
- **对高质量数据的依赖。** 音乐生成模型需要数万小时的授权音乐数据。2024 年发生的 Suno 与 Udio 诉 RIAA 的诉讼事件使这一问题受到了广泛关注。
- **语音克隆的伦理问题。** 只需 3 秒的语音样本加上一段文本提示，VALL-E、XTTS 和 ElevenLabs 就能够克隆出相应的语音。因此，每一个生成模型都需要具备滥用检测功能以及用户选择退出的机制。

## 练习题

1. **简单。** 运行 `code/main.py` 并显式设置样式。验证生成的序列是否符合该样式的模式。
2. **中等难度。** 添加延迟并行解码功能：模拟两股必须保持一步偏移的令牌流，并训练一个联合预测器。

## 生产注意事项：音频处理属于流式处理问题。

音频是用户期望能够*即时生成*的输出模态，而非一次性全部输出。从生产环境的角度来看，输出每个token所需的时间（TPOT）至关重要，因为用户的听觉速度才是目标吞吐量——而非阅读速度。对于以约75个tokens/秒的速率进行分词处理的16kHz音频（使用Encodec），服务器必须为每位用户生成≥75个tokens/秒的内容，才能保证流畅播放。

这会带来两种架构层面的后果：

- **基于流匹配的音频模型无法实现简单流式传输。** Stable Audio 2.5和AudioCraft 2会在单次处理中渲染固定长度的音频片段。若要实现流式传输，则需要将片段分割并使边界重叠——类似于滑动窗口扩散技术——这会比使用编解码器AR模型的方式增加100-300毫秒的延迟开销。

如果产品是“实时语音聊天”或“实时音乐续奏”，应选择编解码器AR路径。而如果是“在提交后渲染30秒长的音频片段”，则基于流匹配的模型在音质和总延迟方面更具优势。
