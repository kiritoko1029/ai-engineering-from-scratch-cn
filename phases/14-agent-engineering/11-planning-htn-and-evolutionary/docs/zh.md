# HTN 与进化搜索的规划

> 符号规划处理计划可证明正确的情况。进化代码搜索处理适应度函数可机器检查的情况。ChatHTN（2025）和 AlphaEvolve（2025）展示了与 LLM 配合时各自能解锁什么。

**类型：** 构建
**语言：** Python（标准库）
**前置要求：** 第 14 阶段 · 02（ReWOO 与 Plan-and-Execute）
**所需时间：** 约75分钟

## 学习目标

- 解释分层任务网络（HTN）：任务、方法、算子、前置条件、效果。
- 描述 ChatHTN 的混合循环——符号搜索加 LLM 后备分解。
- 解释 AlphaEvolve 的进化循环及其为何只在有编程式评估器时才有效。
- 用标准库实现一个简易 HTN 规划器和一个简易进化搜索。

## 问题所在

ReWOO（第 02 课）、Plan-and-Execute 和 ReAct 覆盖了大多数智能体规划。两种它们覆盖不好的情况：

1. **可证明正确性的规划。** 调度、航线规划、合规工作流——计划必须在构造上是健全的。一个流畅但偶尔幻觉步骤的 LLM 计划是不可接受的。
2. **具有机器可检查适应度函数的优化。** 矩阵乘法、调度启发式、编译器遍——目标不是"一个正确的计划"而是"最佳的计划"。

HTN 规划和 AlphaEvolve 解决的是两个不同的问题。两者都将 LLM 用作放大器而非替代品。

## 概念说明

### 分层任务网络

一个 HTN 是：

- **任务**——复合（待分解）和原始（直接可执行）。
- **方法**——将复合任务分解为子任务的方式，带前置条件。
- **算子**——带前置条件和效果的原始动作。
- **状态**——一组事实。

规划：给定目标任务和初始状态，找到一个分解为原始算子的序列，使其前置条件按顺序满足。

HTN 比 LLM 更古老，仍是可证明正确计划的参考。

### ChatHTN（Gopalakrishnan 等人，2025）

ChatHTN（arXiv:2505.11814）交替进行符号 HTN 和 LLM 查询：

1. 尝试用现有方法分解当前复合任务。
2. 如果没有方法适用，询问 LLM："你在状态 `s` 下如何分解 `task`？"
3. 将 LLM 响应翻译为候选子任务。
4. 对算子 schema 进行验证；拒绝无效分解。
5. 递归。

论文的核心主张：产出的每个计划都是可证明健全的，因为 LLM 建议仅作为候选分解进入，而非直接编辑计划。符号层拥有正确性；LLM 扩展方法库。

在线方法学习（OpenReview `gwYEDY9j2x`，2025 后续）添加了一个通过回归泛化 LLM 产出的分解的学习器——将 LLM 查询频率削减高达 75%。

### AlphaEvolve（Novikov 等人，2025）

AlphaEvolve（arXiv:2506.13131，DeepMind，2025 年 6 月）是另一回事：由 Gemini 2.0 Flash/Pro 集成编排的进化代码搜索。

循环：

1. 从种子程序加编程式评估器（返回适应度分数）开始。
2. LLM 集成提出变异。
3. 将变异通过评估器运行。
4. 保留最佳的；再次变异。

已发表的成果：

- 56 年来首次对 4x4 复数矩阵乘法超越 Strassen 的改进（48 次标量乘法）。
- 通过 Borg 调度启发式恢复 Google 计算资源的 0.7%。
- 在前沿工作负载上 FlashAttention 加速 32%。

硬约束：适应度函数必须是可机器检查的。对散文答案的进化搜索不会收敛。

### 何时使用哪种

| 问题类别 | 使用 | 原因 |
|---------|------|------|
| 带硬约束的调度 | HTN + ChatHTN | 可证明的健全性 |
| 编译器优化 | AlphaEvolve | 机器可检查的适应度 |
| 多步骤任务执行 | ReAct / ReWOO | LLM 在环，无形式化保证 |
| 带测试的代码改进 | AlphaEvolve | 测试就是评估器 |
| 策略绑定的自动化 | HTN | 前置条件编码策略 |

### 此模式出错的地方

- **没有算子的 HTN。** 没有前置条件/效果 schema，健全性主张就崩塌了。ChatHTN 的"LLM 建议分解"需要 schema 来拒绝无效操作。
- **没有真实评估器的 AlphaEvolve。** "问 LLM 代码是否更好"不是适应度函数。评估器必须是确定性的和快速的。
- **过度工程。** 大多数智能体任务不需要两者。先尝试 ReAct 或 ReWOO。

## 开始构建

`code/main.py` 实现了两个简易实现：

- 一个标准库 HTN 规划器，带算子、方法、前置条件、效果，以及在没有方法匹配复合任务时启动的 `LLMFallback`。"LLM"是脚本化的分解器，规划器可离线运行。
- 一个标准库进化搜索，在算术程序上进行：增长输出最小化 `|f(x) - target|` 的表达式（在测试集上）。评估器是确定性的。

运行它：

```
python3 code/main.py
```

轨迹展示了 HTN 规划器分解复合任务（中途有 LLM 后备）和进化循环收敛到目标表达式。

## 使用它

- **HTN 规划器**——`pyhop`、`SHOP3`，或为领域特定策略执法构建自己的。
- **ChatHTN**——研究代码；该模式（符号 + LLM 后备）可干净地移植到任何 HTN 规划器。
- **AlphaEvolve**——DeepMind 论文；该模式（集成 + 评估器）可复现。OpenEvolve 和类似的开源分支正在出现。
- **智能体框架**——目前没有一等的 HTN 或 AlphaEvolve。作为子智能体或后台工作构建。

## 交付它

`outputs/skill-hybrid-planner.md` 生成一个混合规划器脚手架（HTN 或进化），LLM 角色显式限定范围。

## 练习

1. 为 HTN 规划器添加回溯：当算子的后置条件在运行时失败时，回滚并尝试下一个方法。
2. 给 ChatHTN 添加 LLM 方法缓存：当 LLM 在状态模式 `P` 下分解任务 `T` 时，存储结果。下次调用时先重新检查方法库。
3. 将进化搜索评估器替换为真实的测试套件。进化一个通过 20 个测试用例的排序函数；报告收敛所需的代数。
4. 阅读 AlphaEvolve 的评估器设计笔记。为你关心的领域设计一个评估器（SQL 查询优化、测试套件最小化、部署 YAML）。
5. 组合：用 HTN 将复合任务分解为子任务，然后对每个子任务的原始算子使用进化搜索。它在哪里出色，在哪里过度工程？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| HTN | "分层规划器" | 带算子、前置条件、效果的任务分解 |
| 方法（Method） | "分解规则" | 将复合任务拆分为子任务的方式 |
| 算子（Operator） | "原始动作" | 带前置条件和效果的具体步骤 |
| ChatHTN | "LLM + HTN" | 没有方法匹配时询问 LLM 的符号规划器 |
| AlphaEvolve | "进化代码搜索" | LLM 集成变异代码；确定性评估器选择 |
| 适应度函数（Fitness function） | "评估器" | 对输出的确定性、机器可检查评分 |
| 在线方法学习（Online method learning） | "缓存的 LLM 分解" | 存储 + 泛化 LLM 计划以削减查询成本 |
